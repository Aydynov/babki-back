# Design

## Context

См. proposal.md — Why. Пользователь выбрал текущие имена с обезличиванием удалённых пользователей и объекты в DTO (2026-10-17).

GroupTransactionsService и GroupTransfersService проверяют доступ через BudgetAccessService/BudgetWriteService, затем вызывают общий финансовый CRUD. Они возвращают raw объекты с createdBy/participantId; mixed history уже добавляет transferResponse/effectiveRate. GroupsService.members отдельно выбирает имена только действующих членов. UserDeletionService немедленно устанавливает deletion_pending и отзывает JWT, а worker позднее очищает персональные поля, оставляя tombstone и групповые финансовые ссылки.

User-модель уже зарегистрирована в TransactionsModule, экспортирующем MongooseModule, и доступна импортирующему его GroupFinancesModule. Новой модели, универсального пользовательского каталога и изменения денежного ядра не требуется. Существующие unit/e2e проверяют денежную изоляцию, права, transfer history и worker удаления.

Обнаружена документальная неточность этапа 05: spec и docs называют discriminator ответа перевода transactionType. Реальная TransactionSchema и HTTP-тесты используют `type`; transactionType является именем query-фильтра. В текущем change уточняется документация/дельта, production-поле не переименовывается, архивы не переписываются.

## Goals / Non-Goals

**Goals:** один пакетный resolver субъектов для всех доступных групповых финансовых ответов, безопасное отображение бывших участников, немедленное сокрытие имён после принятого удаления и сохранение денежных/авторизационных правил.

**Non-Goals:** snapshot имён, новый публичный endpoint по userId, полный исторический каталог членов, имена в приглашениях, deletedByActor, изменение личного API или новых планов/долгов. Последующие групповые адаптеры планов/долгов смогут использовать тот же service.

## Decisions

### 1. Дополнение ответа в групповых адаптерах

Добавить один GroupFinancialActorsService и явный тип GroupFinancialActor в group-finances. Он получает уже разрешённые записи, собирает уникальные createdBy и participantId и возвращает новые объекты с краткими сведениями. Не менять сохранённую операцию, discriminator, идентификаторы, суммы, author checks или shared TransactionsService lookup, используемый для мутаций.

Вызовы из GroupTransactionsService и GroupTransfersService выполняются только после существующих проверок доступа и owner-scoped lookup. Список сначала ограничивается финансовыми фильтрами и пагинацией, затем обогащается одной пачкой; total/page/limit не меняются. Смешанная история сохраняет transferResponse. Нельзя передавать клиентские userId напрямую в resolver или искать профили по participantId query до получения операций.

Create/PATCH обогащаются **внутри** существующего BudgetWriteService callback с той же ClientSession; ошибка чтения actor откатывает финансовую транзакцию, вместо закоммиченных денег с неуспешным HTTP-ответом. DELETE сохраняет 204 без actor lookup. Прочие reads используют существующий режим чтения без записи/увеличения mutationVersion. Не переносить обогащение в контроллеры и не дублировать его в личных сервисах.

Альтернатива — populate в каждой discriminator-модели: оно подменило бы существующие идентификаторы объектами и продублировало правила приватности. Отдельный batch endpoint потребовал бы дополнительного протокола, разрешений и запросов фронта; пользователь выбрал inline DTO.

### 2. Точный actor DTO

createdByActor обязателен для корректной групповой операции. participantActor присутствует только у расхода с сохранённым participantId; у дохода/перевода его нет. Старый participantId отсутствующего legacy-расхода не выдумывается. Оба объекта имеют одинаковую форму:

```json
{
  "userId": "<строка исходного идентификатора>",
  "firstName": "Анна",
  "lastName": null,
  "isAnonymized": false
}
```

firstName/lastName — string либо null, отсутствующее поле профиля нормализуется в null; пустые сохранённые строки не исправляются этим change. isAnonymized означает, что профиль не разрешён как активный; он не раскрывает отдельный status/причину. Для tombstone, deletion_pending и отсутствующего документа оба имени null, isAnonymized=true, userId прежний. Локализованный текст «Удалённый пользователь» формирует фронт; API не смешивает его с настоящим именем.

Клиент не задаёт actor-объекты: действующие strict DTO отвергают неизвестные поля. Исходные createdBy/participantId остаются ObjectId-строками в JSON. Не расширять identity-проекцию случайными полями Mongoose-документа.

### 3. Текущий профиль и приватность удаления

Пакетный запрос выбирает только `_id` из разрешённых строк и `status: active`, проекция `_id firstName lastName`. Таким образом имена deletion_pending/deleted даже не загружаются в resolver. Отсутствующий в выборке ID получает обезличенный actor; ошибка запроса не превращается в пустую выборку. Для пустой страницы запроса профилей нет. Один Map сопоставляет результаты, включая повтор одного человека как автора и участника; N+1 запросы не допускаются.

Имя берётся заново при каждом вызове, независимо от текущего членства отображаемого человека; persistent cache и snapshot не добавляются. Выход/исключение не скрывает имя активного профиля от оставшихся участников, но не возвращает бывшему участнику доступ. Каталог members не расширяется. После deletion request новые чтения скрывают имя до запуска worker; завершение worker не меняет actor DTO. Существующие данные/аудит не переписываются.

Конкурентные чтения могут видеть профиль на момент своего чтения; в финансовой мутации — snapshot её сессии. Ответ начатого до удаления запроса может отражать ранее прочитанный профиль, но следующий запрос после принятого удаления обезличен. Никакого нового кеша, который продлевал бы раскрытие имени, нет. Учёт остатков/права не зависят от показанного имени.

### 4. Ошибки и совместимость

Недоступные объекты/бывший вызывающий получают прежний 404 до user lookup; отсутствие JWT — 401, недостаточные права — прежний 403. Неизвестный participantId filter возвращает пустую страницу без профиля. Пропавший профиль, на который **есть сохранённая ссылка**, не делает операцию недоступной: возвращается безопасный fallback.

Сбой User.find даёт существующий нормализованный 500 в read-пути или 503/rollback через BudgetWriteService в mutation-пути; нет ad hoc filter и успешного ложного обезличивания. Личные wrappers, revenue/reports, управление членством и DELETE не получают дополнительных identity lookup. Клиент со строгой схемой должен принять новые поля.

### 5. Проверки

До изменения — characterization личного API и существующих групповых контрактов; новый HTTP RED подтверждает отсутствие actor-полей. Unit resolver проверяет точные поля/projection, один query для страницы, dedup/empty, session propagation, не-мутирование входа, обезличивание и ошибку хранилища.

HTTP на существующем startGroupsTestApp проверяет все create/PATCH/list/detail для expense/income/transfer и mixed history; раздельные author/participant, переименование/выход/исключение/повторное вступление, архивные счета, исторический participantId-filter и две группы плюс личный бюджет. DTO injection — 400, каталог членов остаётся active-only. Exact keys исключают email/description/auth/status и лишние profile-поля.

Для удаления использовать настоящий UserDeletionService.request и UserDeletionWorker, а не только ручную смену status: pending с ещё сохранёнными именами, затем worker tombstone, неизменные ссылки и деньги. Пропавший профиль проверить отдельно raw fixture. Read failure и failure actor lookup после финансовой записи должны сохранить нормализованные ошибки и атомарный rollback create/PATCH; оба transfer effects тоже откатываются. Проверить read после committed rename/deletion без кеша и совместимость текущих permission/concurrency suites.

## Risks / Trade-offs

- Старое имя в UI после rename/удаления → сервер не кеширует; docs просит обновлять историю, локальный frontend cache вне этапа.
- Дополнительный запрос на страницу → один ограниченный $in по ID только её строк, существующий индекс User._id.
- Финансовая мутация зависит от identity-read → та же сессия гарантирует rollback при ошибке, без частичного успешного списания.
- Смешивание атрибуции и прав → сырые ссылки и существующие authority checks не заменяются DTO-полями.
- Бывший участник виден по имени → это согласованная пользователем политика текущего активного профиля; удаляемые профили обезличиваются сразу.

## Migration Plan

Миграции/reset/новые индексы/env/секреты не нужны. Развёртывание добавляет поля к групповой выдаче; старые записи разрешаются по прежним ссылкам. Откат убирает actor-поля, не восстанавливает очищенные персональные данные и не меняет деньги. После реализации/проверок/ревью: коммит реализации без co-authored → sync group-transactions с сохранением Purpose/прежних сценариев → архив → второй коммит. Дорожная карта фиксирует точные проверки и оба действия; этап 08 планируется отдельно.
