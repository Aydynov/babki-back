# Design

## Context

См. proposal.md для причины изменения. AccountsService формирует amount через balanceForBudget; снимки уже рассчитываются на конец месяца. Этот же низкоуровневый расчёт используется для исторических отчётов и проверки средств на дату перевода, поэтому его семантику необходимо сохранить.

## Goals / Non-Goals

**Goals:** применять одну границу месяца в ответах счетов и использовать одну дату расчёта для всех счетов одного списка.

**Non-Goals:** изменение состава timeline, исторических дат отчётов, проверки средств на дату перевода и формата HTTP-ответов.

## Decisions

- Создание и общий сборщик ответов AccountsService передают существующий utcMonthEnd(new Date()) в balanceForBudget. Для списка граница вычисляется один раз.
- Альтернатива — округлять дату внутри balanceForBudget — отклонена: это изменило бы исторические расчёты и проверку средств на конкретную дату.
- Альтернатива — брать последний снимок — отклонена: последний снимок может относиться к следующему месяцу, а баланс должен учитывать только текущий месяц.
- Реальный HTTP-регрессионный тест на временном MongoDB replica set проверяет обе стороны перевода, список, детали, rename, исключение следующего месяца и начальный остаток при будущем openedAt.

## Risks / Trade-offs

- Клиенты, трактовавшие amount как баланс на момент запроса, получают другую сумму при будущих операциях → семантика явно изменена в спецификации и документации API.
- Проверка средств при переводе остаётся на дату перевода, поэтому она может отличаться от отображаемого месячного amount → это сохраняет существующее требование Atomic and reproducible balances.

## Migration Plan

Изменение уже реализовано и проверено в рабочем дереве. Миграция данных и пересоздание снимков не нужны. При откате достаточно вернуть передачу текущей даты в ответах AccountsService и прежнее описание amount.
