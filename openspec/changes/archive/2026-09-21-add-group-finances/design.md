## Context

Мотивация и функциональные границы описаны в proposal.md. Сейчас Account, Transaction, ExpenseCategory и ExpenseLimit используют userId как владельца. Создание расхода/дохода автоматически выбирает личный balance. Снимки принадлежат accountId, но сервис авторизует их через личного владельца. Отчёты и остатки лимитов фильтруют userId. Discriminator type различает balance/saving и income/expense/save.

GroupsAccessService уже проверяет текущее членство и сериализует мутации записью mutationVersion группы внутри транзакции. Этот протокол используется жизненным циклом группы и приглашениями, поэтому его можно распространить на финансовые операции без отдельной системы блокировок.

В затрагиваемом коде есть риски: удаление операций и счетов не полностью транзакционно, проверки снимков выполняются вне переданной session, сравнение месяцев не учитывает год, увеличение расхода пересчитывает баланс с положительным знаком, расчёт остатка лимита превращает любую ошибку в нулевой расход. Эти места необходимо исправить в рамках выделения общего финансового ядра и покрыть регрессиями.

## Goals / Non-Goals

**Goals:** единая финансовая логика для личного и группового бюджета, явная граница авторизации, неизменяемая принадлежность данных, совместимость личного API, содержательный development seed и сериализуемые финансовые изменения.

**Non-Goals:** отдельный бухгалтерский движок, произвольные роли/политики, многовалютность, несколько основных счетов на группу, групповые накопления и переводы, переустройство личных долгов и планов. Код приложения не меняется в ходе подготовки change.

## Decisions

### 1. Общий контекст бюджета вместо копии финансовых модулей

Ввести discriminated union BudgetContext: `{ ownerType: 'user' | 'group', ownerId }`. Сервис доступа получает actorId отдельно от бюджета; личный контекст строит сервер по JWT, групповой — по groupId маршрута после проверки членства. В финансовом коде запретить использование actorId как фильтра принадлежности.

Расширить схемы Account, Transaction, ExpenseCategory и ExpenseLimit обязательной парой ownerType/ownerId. userId сохраняется для совместимых личных записей/ответов; у групповых записей его нет. Все новые ссылки Mongoose задаются через Schema.Types.ObjectId. Нельзя использовать владельца группы как владельца её финансовых объектов. Промышленная база для первого развёртывания этой структуры считается пустой, поэтому backfill legacy-документов не входит в change.

Snapshot сохраняет accountId как единственный источник принадлежности. Внутренние методы чтения снимков получают только уже проверенные счета; внешние маршруты всегда разрешают контекст через сервис доступа. Сохранить discriminator type и текущую регистрацию моделей.

Альтернативы: копия всех финансовых сервисов для групп быстро разойдётся в исправлениях; только необязательный groupId оставляет userId одновременно автором, участником и владельцем, создавая риск утечек в старых запросах. Явная пара владельца выбрана для однозначности. Циклические зависимости categories ↔ expenses заменить узкими проверками ссылок/репозиториями там, где требуется для общего ядра.

### 2. Права как данные членства

Добавить permissions с тремя булевыми ключами manageAccounts, manageCategories, manageLimits; отсутствующее значение интерпретируется как false. Владелец определяется исключительно Group.ownerId, получает все права независимо от сохранённого набора. Только текущий владелец изменяет права другого active-участника через PATCH; отдельная роль администратора не вводится.

PATCH принимает непустое подмножество известных булевых полей; неуказанные сохраняются, null и преобразование строк в bool запрещены. Ответ и записи GET members содержат все три effective permissions. Изменение владельца через permissions невозможно (409).

Выход/исключение сбрасывают permissions. При повторном вступлении набор явно записывается пустым; передача владения сбрасывает сохранённые наборы прежнего и нового владельца, чтобы прежние делегирования не всплыли при следующей передаче. Передача не меняет права остальных участников. Расширить историю членства событием permissions-updated с before/after, actorId и targetUserId; сбросы при выходе/передаче отражать в соответствующих событиях. Права не помещаются в JWT.

### 3. Авторство и атрибуция

Transaction получает createdBy; Expense дополнительно participantId. Для личных операций createdBy и participantId расхода равны ownerId; клиент не задаёт автора. У группового дохода participantId отсутствует. Создание групповой операции требует accountId и проверяет соответствие groupId маршрута владельцу счёта; categoryId проверяется в том же контексте.

Изменение расхода: owner либо active createdBy либо active participantId. Переназначение participantId доступно owner/createdBy и только на active-участника. Если participantId не изменён, бывший участник сохраняется. Доход изменяет owner/active createdBy. Делегирование настроек не расширяет эти правила.

PATCH расхода включает amount, description, merchant, items, categoryId, participantId; PATCH дохода — amount, description. Дата и счёт неизменяемы в этом этапе, исправление даты требует отменить запись и создать новую. Приватные поля пользователей не populate; достаточно идентификаторов автора и участника. Фильтр participantId — по сохранённой записи, без обязательного active-членства фильтруемого пользователя.

Групповые операции удаляются логически (deletedAt/deletedBy), с обратным изменением баланса в той же транзакции; все суммы и выдачи исключают удалённые записи. Повторное удаление возвращает 404 и не компенсирует сумму второй раз. Личные ответы сохраняют текущую форму, внутренние ownerType/ownerId/createdBy не просачиваются через lean/spread.

### 4. Кошелёк и расчёт баланса

Один групповой balance создаётся явно с начальной суммой (по умолчанию 0), initialAmount и openedAt. Начальный остаток действует с openedAt. Групповые операции раньше openedAt возвращают 400; клиент задаёт openedAt при создании при необходимости внести историю, по умолчанию серверное текущее время. Дата валидируется как ISO; менять openedAt после создания нельзя. До openedAt отчёт показывает нулевой баланс.

На group-счёт добавить уникальный частичный индекс ownerType/ownerId/type; повторное создание 409. Удаление пустого счёта возможно только при initialAmount=0 и отсутствии операций, включая логически удалённые. Это даёт manageAccounts конкретные полномочия создания/удаления кошелька без возможности стереть историю. Настройки суммы через произвольную запись snapshot не открываются.

Общий механизм изменения остатков принимает signed delta: create income +amount, expense -amount; update expense old-new; delete expense +old, income -old. Вычисление diff берёт старую запись внутри транзакции. Суммы на границах вычислений нормализуются до двух знаков; переход всего хранилища на новую денежную единицу вне scope. Отрицательный расчётный остаток разрешён у group, потому что сервис регистрирует фактические операции, а не проводит банковские платежи.

Групповые снимки — производный кэш остатков конца календарного месяца (UTC), учитывающий initialAmount и активные операции. При изменении прошлой операции пересчитать затронутый и последующие существующие месяцы, создать отсутствующий месяц; для пустых промежуточных периодов отчёты переносят последний остаток. Даты конца отчётного периода проверяются явно. Не смешивать начальную сумму с первым приходом. Личные правила периодов и ручных снимков сохраняются; общее ядро не должно переинтерпретировать старые снимки.

### 5. Транзакции и конкурентный доступ

Для каждой group-мутации: начать транзакцию → serializeMutation(groupId, session) → повторно requireMember/requireOwner/requirePermission внутри session → загрузить счёт и связанные объекты в том же контексте/session → изменить запись и баланс → commit. При повторе withTransaction вся авторизация выполняется заново. Все групповые settings-операции, назначения прав и удаления счетов следуют тому же протоколу. Проверки ссылок, архива категории, истории счёта и целевого участника выполняются после сериализации.

Это сериализует финансовые записи одной группы и изменения её доступа, предотвращая write skew. Личные мутации общего ядра используют запись версии account как точку конфликтов; для личных save блокировать оба счёта в стабильном порядке по ObjectId. MongoDB session не используется параллельно через Promise.all. Ошибки не маскируются под успешный нулевой результат. Запись события/снимка и изменение операции откатываются вместе.

### 6. Категории, лимиты и отчёты

Категории используют уникальный индекс ownerType/ownerId/name вместо userId/name. Архивная категория остаётся видимой для истории; новые назначения запрещены, изменение суммы старого расхода с неизменённой категорией разрешено. Удаление запрещено при любой ссылке из расхода или лимита. Проверка и удаление выполняются под group-lock.

Лимиты: включительные startDate/endDate нормализуются к началу/концу дня UTC для новых групповых маршрутов; отсутствие дат означает текущий календарный месяц UTC. Проверять start<=end и пересечение всех периодов той же категории, а не только текущей даты. PATCH меняет total/startDate/endDate, категория неизменяема. Пересечение проверяется без самой изменяемой записи внутри транзакции. Ошибка расчёта расходов возвращается клиенту, не превращается в ноль.

Групповые месячные/годовые отчёты повторяют структуру текущих отчётов, используют выбранный budget и счета, не список действующих участников. participantId поддерживается в списке расходов и expenses/revenue, но не в общем отчёте с балансом: отклонять такой query 400, чтобы не выдавать общий баланс за индивидуальный.

### 7. HTTP-контракт

Все маршруты под текущим API prefix с @CurrentUser, глобальными JWT/DTO/error mechanisms. groupId, memberId и финансовые ObjectId валидируются, сравнения регистронезависимы через ObjectId.equals. Недоступный контекст/объект 404, недостаточные права active-участника 403, конфликт состояния 409, некорректный DTO 400. Инфраструктурный сбой транзакции 503. На все списки операций действует существующая пагинация.

| Маршрут относительно /groups/:groupId | Методы и назначение |
| --- | --- |
| /members/:userId/permissions | PATCH → 200, только owner |
| /accounts | GET → 200 список; POST → 201 {amount?, openedAt?}, manageAccounts |
| /accounts/:accountId | GET → 200; DELETE → 204 пустой счёт, manageAccounts |
| /expenses | GET → 200; POST → 201 {accountId, categoryId, participantId?, amount, transactionDate, description?, merchant?, items?} |
| /expenses/revenue | GET → 200 сумма с теми же фильтрами расходов |
| /expenses/:expenseId | GET/PATCH → 200; DELETE → 204 |
| /incomes | GET → 200; POST → 201 {accountId, amount, transactionDate, description?} |
| /incomes/:incomeId | GET/PATCH → 200; DELETE → 204 |
| /transactions | GET → 200 объединённая история с фильтрами даты, типа и счёта |
| /expense-categories | GET → 200; POST → 201, manageCategories |
| /expense-categories/:categoryId | GET/PATCH → 200; DELETE → 204, мутации manageCategories |
| /expense-limits | GET → 200; POST → 201, manageLimits |
| /expense-limits/:limitId | GET/PATCH → 200; DELETE → 204, мутации manageLimits |
| /reports/months, /reports/years | GET → 200 |

Личные маршруты остаются личными даже при передаче идентификатора группового счёта. Новый групповой маршрут не вызывает личный контроллер с подставленным ownerId. Для группы не открывать произвольные routes snapshots или saves. Неизвестные query/DTO поля отклоняются; GET accounts до явного создания возвращает пустой список, group reports — нулевые агрегаты, создание операции без существующего счёта — 404.

## Risks / Trade-offs

- Сериализация на группе ограничивает её throughput → приемлемо для семей и небольших организаций; не заменять её до появления измеренной нагрузки.
- Много старых userId-фильтров и агрегатов → инвентаризация всех финансовых путей, seed/auth initialization и тест личного пользователя с двумя группами; явные проекции ответов.
- Изменение общих схем может затронуть личные savings/debts/plans → сохранить discriminator, личные адаптеры и запускать полные регрессии, включая вызовы с внешней session.
- Новая структура несовместима с legacy-документами без owner-полей → первый промышленный rollout выполняется только на пустой базе; при появлении живых legacy-данных потребуется отдельный change миграции.
- Number имеет ограничения точности → граничные тесты дробных сумм и округление до двух знаков; новая валютная модель не добавляется.
- Политики одного кошелька, отсутствия групповых переводов, открывающей даты и отрицательного учётного остатка — проектные решения этого этапа, подлежащие ревью вместе со спецификациями.

## Initial data and development seed

1. Первый промышленный rollout создаёт коллекции и индексы из актуальных Mongoose-схем на пустой базе. Автоматический backfill и startup barrier отсутствуют.
2. Все новые личные записи сразу получают ownerType=user, ownerId=userId и серверное авторство; групповые записи создаются только через групповые сервисы.
3. Development seed очищает локальную базу и создаёт четыре пользователя с единым известным паролем, существующий насыщенный личный бюджет главного пользователя, семью, две организации и отдельную пустую группу.
4. Семья содержит владельца, участников с полным и частичным делегированием, бывшего участника с историей, общий кошелёк, категории, лимит, доходы и расходы, включая расход автора за другого участника.
5. Обе организации имеют независимые кошельки и операции одного пользователя, а права на настройки различаются. Это позволяет вручную проверить изоляцию его личных расходов и двух рабочих бюджетов.
6. Пустая группа не имеет кошелька и содержит активное приглашение с токеном, который seed печатает в stdout; она покрывает явное создание кошелька и вступление по приглашению.
7. Даты seed вычисляются относительно текущего месяца, чтобы текущие отчёты и лимиты оставались содержательными. Seed разрешён только при NODE_ENV=development.
