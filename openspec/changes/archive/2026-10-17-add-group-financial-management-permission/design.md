# Design

## Context

См. `proposal.md` для мотивации и `specs/` для контракта. Сейчас `GroupPermissions` содержит три независимых права; общий `permissionFields` используется в схемах членства и событий. `effectivePermissions` уже централизует права владельца и значения по умолчанию. `GroupsService.updatePermissions` принимает частичное изменение, пишет аудит и работает через транзакцию с сериализацией группы. Выход, исключение и передача владения используют общий сброс прав.

`GroupTransactionsService.change` проверяет владельца, автора и participantId внутри `GroupFinanceWriteService.run`. Обёртка блокирует конкурирующие мутации через `mutationVersion`, проверяет актуальное членство и выполняет финансовый пересчёт в одной MongoDB-транзакции. Групповые DTO формируются через `GroupsService.toDto`; сегодня там только `role`, а `permissions` вычисляются для каталога участников.

Модели Account/Transaction уже общие и содержат `ownerType/ownerId`; имеется `BudgetContext`. Последующая универсализация механизмов предусмотрена этапом 02 дорожной карты. Этот change расширяет общую политику группового доступа и не создаёт финансовых сущностей или сервисов-дубликатов.

## Goals / Non-Goals

**Goals:** использовать существующие разрешения, аудит, DTO и транзакции; не менять финансовую арифметику; сделать собственные права доступными без поиска в каталоге; сохранить личные контракты и существующие права обычного участника.

**Non-Goals:** новые переводы/планы/долги, финансовая роль администратора, произвольные наборы ролей, смена валютной модели или массовый рефакторинг финансов. Политика доступа для будущих сущностей будет подключена в соответствующих change.

## Decisions

### 1. Одно независимое право manageTransactions

Добавить булево поле в `GroupPermissions`, `permissionFields`, `effectivePermissions` и `UpdateGroupPermissionsDto`. Это следует существующему делегированию; отдельная роль потребовала бы второй системы разрешений, а расширение manageAccounts смешало бы управление счетами и чужими операциями. Никаких новых прав по умолчанию для участников. Сохранить строгую проверку булевых значений, запрет null, неизвестных полей и пустого PATCH.

Матрица операций:

| Действие | Владелец | Автор | Участник расхода | manageTransactions | Только права настроек |
| --- | --- | --- | --- | --- | --- |
| Создать доход/расход | Да | Любой действующий участник | Любой действующий участник | Да | Да |
| Изменить/удалить доход | Да | Да | Не применимо | Да | Нет дополнительных прав |
| Изменить/удалить расход | Да | Да | Да | Да | Нет дополнительных прав |
| Переназначить расход | Да | Да | Нет дополнительных прав | Да | Нет дополнительных прав |
| Выдать права/управлять группой | Да | Нет дополнительных прав | Нет дополнительных прав | Нет | Нет |

Все разрешения предполагают действующее членство. Переназначение требует действующего получателя той же группы. Историческая атрибуция сохраняется при изменении других полей. Валидаторы, доступ к объекту и запрет изменения immutable-полей остаются прежними.

### 2. Проверять актуальную политику внутри существующей транзакции

Разрешение мутации — владелец OR автор OR применимая атрибуция OR manageTransactions. Добавить небольшой общий метод чтения эффективных прав в `GroupsAccessService`, используемый и сериализацией, и проверкой операции; он принимает текущую сессию. Отсутствие права возвращает false для этой ветки, чтобы не запрещать автору собственную операцию. Не делать обязательный `requirePermission(manageTransactions)` для всех изменений: это нарушит права автора/участника.

Сначала разрешить принадлежность целевого объекта бюджету, затем полномочия: иностранный объект возвращает 404, недостаточные права на доступный объект — 403. Проверять право и действующее членство в той же сессии после сериализации группы. Проверка из JWT или только в контроллере не обеспечивает отзыв с прежним токеном и согласованность конкурентных запросов.

Сохранить автора и текущий механизм deletedBy. Дополнительный журнал всех финансовых правок здесь не вводится; аудит выдачи/отзыва прав уже существует и расширяется.

### 3. Возвращать permissions во всех DTO группы

Сериализатору передавать заранее полученные эффективные права; чтение членства не прятать в функцию форматирования. В списке групп использовать уже прочитанные активные членства, расширив projection `groupId` до нужных полей, и сопоставлять их по groupId. Не вызывать каталог участников и не добавлять N+1-запросы.

Для чтения конкретной группы использовать общий механизм доступа. При создании, изменении и передаче владения вычислять контекст по данным текущей транзакции; ответ передачи относится к инициатору, который уже стал обычным участником. Важно обновить все места вызова `toDto`, а не только GET. `role` и `permissions` должны относиться к одному состоянию роли/членства; мутации в любом случае повторно проверяют доступ.

### 4. Расширять общие механизмы, сохраняя границы бюджетов

Не заводить GroupPermissionV2, новый кошелёк, отдельные копии Account/Transaction или дополнительный реестр ролей. Существующий механизм разрешений остаётся одной точкой групповой политики и сможет использоваться общими финансовыми сервисами через BudgetContext. Личный бюджет проверяется по своему владельцу и не получает зависимость от членства в группе. Общие вычисления и доступ универсализируются следующим change без изменения правил отрицательного баланса и личных ограничений.

## Risks / Trade-offs

- [Поле не хранится в старых членствах] → `effectivePermissions` трактует отсутствие как false; владелец получает true по роли. Регрессия проверяет запись, реально сохранённую без поля.
- [Отзыв конкурирует с правкой] → сохранить существующую сериализацию группы и одну сессию; e2e использует управляемые барьеры, а не ожидания по времени.
- [Расширение схемы прав ломает строгий клиент] → документировать полный объект и примеры; фронт должен обновить схему до развёртывания нового ответа.
- [Забытый сброс или неполный аудит] → проверить вступление/выход/исключение/повторное вступление/передачу и вложенные permissionResets, не переписывая старые события.
- [Права в ответе устаревают после получения] → сервер проверяет каждый запрос заново; ответ отражает состояние на момент чтения и не является разрешением на будущую запись.

## Migration Plan

1. Обновить контракт фронта для четырёх прав и permissions в DTO группы. Новое право включается владельцем явно.
2. Развернуть код с безопасным чтением старых членств. Поле не заполнять true при миграции; не менять три существующих значения. Старые события аудита оставить историческими.
3. Проверить сценарий выдача → чужая правка → отзыв → 403 с прежним JWT и изоляцию личного бюджета/второй группы.
4. Откат кода прекращает новые полномочия делегата; сохранённое поле можно оставить, данные операций не требуют отката. Перед повторным включением после отката проверить сохранённые назначения и при необходимости явно отозвать их. Документировать временное исчезновение permissions из старого DTO при откате.
