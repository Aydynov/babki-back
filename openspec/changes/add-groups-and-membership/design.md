## Context

Мотивация и границы изменения описаны в proposal.md. Сейчас счета, категории, транзакции и отчёты привязаны к userId; TransactionsService автоматически находит личный счёт. Их изменение отложено. Приложение использует MongoDB replica set, Mongoose, глобальный JWT guard, строгий ValidationPipe и @CurrentUser(). RequestLoggingInterceptor и HttpExceptionFilter используют request.url, поэтому секрет приглашения нельзя передавать в URL API.

## Goals / Non-Goals

**Goals:** независимый модуль групп; единая проверка доступа для последующего использования финансовыми модулями; атомарные переходы членства и приглашений; сохранение стабильных идентификаторов.

**Non-Goals:** универсальная ACL-система, изменение JWT и TOTP, финансовые миграции, клиентский экран принятия ссылки, почтовая доставка. Финансовые ограничения proposal фиксируют следующий change и не означают добавление неиспользуемых полей в текущие финансовые схемы.

## Decisions

### 1. Один доменный GroupsModule

Разместить контроллеры, DTO, схемы и сервисы групп, членства и приглашений в src/modules/groups; зарегистрировать модуль в AppModule. Экспортировать GroupsAccessService с проверкой действующего членства/владения и поддержкой session для будущих потребителей. Контроллеры получают вызывающего только через @CurrentUser().

Альтернатива — отдельные взаимозависимые модули для каждого документа — добавляет связи без самостоятельных доменных границ. Один модуль сохраняет внутренние операции согласованными.

### 2. Модель данных и история

- Group: name, type (family | organization), description, ownerId, deletedAt, mutationVersion, timestamps. ownerId — единственный источник роли владельца; роль в DTO вычисляется по нему. Индекс ownerId для административных проверок; списки доступны через членство.
- GroupMembership: groupId, userId, status (active | left | removed), joinedAt, endedAt, timestamps. Уникальный индекс (groupId, userId); индекс (userId, status, groupId) для списка групп. При повторном вступлении обновляется та же запись.
- GroupMembershipEvent: groupId, userId, actorId, kind (joined | left | removed | ownership-transferred | group-deleted), occurredAt; при передаче хранить предыдущего и нового владельца. Добавлять события в той же транзакции; индекс (groupId, occurredAt, _id). История отдельно от текущего состояния не создаёт растущий массив внутри документа. Удаление группы фиксируется одним событием; её deletedAt прекращает эффективное членство всех участников, без массового обновления их документов.
- GroupInvitation: groupId, createdBy, tokenDigest (select:false), expiresAt, status (pending | accepted | revoked), acceptedBy/acceptedAt, revokedBy/revokedAt, timestamps. Уникальный индекс tokenDigest; индекс (groupId, createdAt, _id). expired вычислять для pending при expiresAt <= now; при удалённой группе приглашение всегда непригодно независимо от поля status. Не ставить TTL на приглашения: сохранять аудит.
- GroupInvitationRateLimit: userId, windowStart, count, expiresAt; уникальный индекс (userId, windowStart), TTL expiresAt для очистки. Фиксированное минутное окно определяется округлением серверного времени вниз до минуты.

Альтернатива с role=owner в каждом членстве дублирует ownerId и требует дополнительных инвариантов. Отдельный ownerId плюс обязательное действующее членство проще. Массив групп в User усложняет историю и поиск; поэтому User не меняется.

### 3. REST-контракт

Все пути ниже относительны глобальному API-префиксу и требуют JWT.

| Метод и путь | Данные / результат | Доступ |
| --- | --- | --- |
| POST /groups | {name, type, description?}; 201 Group | Авторизованный пользователь |
| GET /groups | page, limit; {items,total,page,limit} | Собственные действующие группы |
| GET /groups/:groupId | 200 Group | Участник |
| PATCH /groups/:groupId | {name?,description?}; 200 Group | Владелец |
| DELETE /groups/:groupId | 204 | Владелец |
| GET /groups/:groupId/members | page, limit; пагинированные участники | Участник |
| POST /groups/:groupId/leave | 204 | Участник, кроме владельца |
| DELETE /groups/:groupId/members/:userId | 204 | Владелец, кроме себя |
| POST /groups/:groupId/ownership | {userId}; 200 Group | Владелец |
| POST /groups/:groupId/invitations | без параметров; 201 {id,token,expiresAt} | Владелец |
| GET /groups/:groupId/invitations | page, limit; метаданные без секрета | Владелец |
| DELETE /groups/:groupId/invitations/:invitationId | 204 для pending | Владелец |
| POST /group-invitations/accept | {token}; 200 {groupId,role:'member'} | Авторизованный получатель |

Group DTO: id, name, type, description при наличии, ownerId, role текущего пользователя, createdAt, updatedAt. Членство DTO: userId, firstName, lastName при наличии, role, joinedAt. Приглашение DTO списка: id, createdBy, createdAt, expiresAt, status, acceptedBy/acceptedAt или revokedBy/revokedAt при наличии. Никаких полных populated User-документов в ответах.

Пагинация соответствует getPagination/PaginationQueryDto, стабильная сортировка по createdAt и _id (участники — joinedAt и _id). Идентификаторы валидировать до запросов; неверный формат — 400. Неизвестные поля отклоняет глобальный pipe. Недоступная группа — 404; недостаточная роль действующего участника — 403. Несуществующий участник/приглашение внутри доступной группы — 404. Повторное удаление группы — 404; повторное исключение недействующего участника — 404. Пустое описание очищается пустой строкой, null не принимается. Тип группы неизменяемый, PATCH без изменений — 400.

### 4. Атомарность через общий документ группы

Любая мутация группы, членства или приглашения выполняется в withTransaction. В начале транзакции условно увеличить mutationVersion неудалённой группы, затем прочитать и проверить права в этой же session. Эта реальная запись создаёт общую точку конфликта для всех мутаций одной группы. Проверка без записи недостаточна: snapshot isolation допускает write skew между выходом участника и передачей ему владения.

При принятии ссылки сначала найти приглашение по digest в session для получения groupId, затем выполнить запись-сериализацию группы, повторно проверить invitation.status, expiresAt относительно текущего времени попытки, членство и состояние группы. Условно пометить pending как accepted, создать/активировать членство и записать событие в одной транзакции. Существующий действующий участник получает 409 с откатом, приглашение не потребляется. Невалидный/терминальный токен получает общий 400. Повторный запрос после успешного принятия той же ссылки получает 400.

При повторении транзакции после конфликта заново получать время и проверять права; не сохранять результат авторизации вне callback. Retry механизма драйвера использовать для transient conflicts; после исчерпания возвращать нормализованную ошибку 503 без частичного результата. Не выполнять внешние эффекты внутри повторяемого callback. Генерация и раскрытие приглашения происходят так, чтобы ответ отправлялся только после commit.

Создание группы и членства владельца атомарно. Передача меняет ownerId только на действующего участника. Удаление устанавливает deletedAt и добавляет событие, поэтому все будущие операции и принятие ссылок отказываются. Старые JWT не дают дополнительных прав. Запрос чтения, начавшийся до отзыва доступа, может завершиться; новые запросы после завершения отзыва обязаны отказать.

Альтернатива — распределённая блокировка — потребовала бы нового сервиса и восстановления блокировок. Конфликт на документе группы достаточен для небольших групп; последовательность записей внутри группы является осознанным ограничением пропускной способности.

### 5. Секреты и ограничения приглашений

Токен — 32 случайных байта node:crypto, base64url; в БД только SHA-256 digest. Случайная энтропия позволяет обойтись без нового ключа конфигурации. Срок 7 суток и лимит 10 запросов/60 секунд зафиксированы как начальные продуктовые значения в specs.

API возвращает token и expiresAt, а клиент строит ссылку на свой экран с токеном во fragment, например /join#token=...; frontend URL не конфигурируется на backend. После авторизации клиент отправляет токен в JSON body на фиксированный путь /group-invitations/accept. GET принятия и токен в query/path API не поддерживаются. Не журналировать тела и не включать токен в ошибки. Перед релизом проверить отсутствие body/response logging на уровне прокси; инструкция клиентской интеграции должна запрещать пересылку токена в query.

Отдельный guard после JWT и до DTO validation считает все авторизованные обращения к accept. Атомарный upsert/$inc по (userId,windowStart) выполняется вне транзакции вступления, чтобы откат не отменял попытку; конкурентный duplicate key повторяется как update. Count > 10 даёт 429 и Retry-After до конца окна. TTL только убирает старые окна. При недоступности счётчика запрос не допускается, возвращается 503. Существующий AuthThrottleService связан с паролями/TOTP, поэтому не расширять его и не менять их лимиты. Использовать стандартный HTTP exception/headers и сохранить глобальный формат ошибок.

### 6. Переход к групповым финансам

Group.id и User.id остаются стабильными после прекращения членства. В следующем change счёт определит scopeType/scopeId, операция сохранит принадлежность бюджету независимо от текущего членства; attributedToUserId и createdBy будут независимы. GroupsAccessService станет точкой проверки текущего доступа, а финансовые мутации должны участвовать в протоколе сериализации с отзывом членства. Групповые категории и снимки баланса также потребуют собственного scope. Не добавлять groupId в User и не считать бюджет объединением личных операций участников.

## Risks / Trade-offs

- [Ссылка передана постороннему] → bearer-приглашение намеренно не адресное, действует один раз и 7 суток; владелец может отозвать его.
- [Перегрузка одной группы] → сериализация мутаций ограничивает throughput; достаточна для текущего масштаба, проверить конкурентными тестами.
- [Забытый фильтр доступа] → все групповые операции через общий access service, HTTP-тесты чужих идентификаторов и прежних JWT.
- [История растёт] → отдельные события с индексами; срок удаления истории не вводится этим change.
- [TTL задерживается] → срок приглашения и окна лимита проверяется логикой, а не очисткой.
- [Границы фиксированного окна] → возможен краткий всплеск на стыке минут; высокая энтропия токенов и лимит делают этот компромисс приемлемым.

## Migration Plan

1. Создать новые коллекции и индексы до включения маршрутов; проверить replica set. Использовать повторяемый способ инициализации индексов, принятый при реализации в репозитории.
2. Развернуть модуль без изменения существующих документов, API, секретов и переменных окружения. Старые пользователи начинают без членств; кошельки не создаются автоматически.
3. Выполнить smoke-сценарий двумя пользователями: создание, приглашение, принятие, передача, выход и удаление, проверив личный бюджет.
4. Для отката отключить новые маршруты/вернуть предыдущую версию приложения, сохранив новые коллекции; при повторном включении история и потреблённые токены сохраняются.
