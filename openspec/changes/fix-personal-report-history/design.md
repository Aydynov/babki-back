# Design

## Context

Мотивация описана в `proposal.md`. ReportsService использует общий `firstSnapshot()` для годового отчёта и начала месячного диапазона по умолчанию. AccountsSnapshotsService.findByUserId возвращает снимки не позднее текущего момента в порядке убывания даты. Сейчас helper берёт первый элемент и ограничивает его началом текущего года. Валютные агрегаты и расчёт остатков уже реализованы отдельно от выбора периодов.

## Goals / Non-Goals

**Goals:** исправить выбор начала диапазона локально в ReportsService и зафиксировать контракт в `personal-report-history`, сохранив общую выдачу снимков и существующие агрегаты.

**Non-Goals:** новые параметры годового endpoint, изменение часового пояса календарных границ, расчёта остатков, групповых отчётов, `/incomes/revenue` или структуры ответов.

## Decisions

### Выбирать минимальную дату внутри ReportsService

Найти минимальную дату среди доступных снимков и вернуть её без ограничения началом текущего года. Выбор минимума не зависит от порядка массива и корректно учитывает несколько счетов. Пустой массив даёт `null`. Удалить ставший неиспользуемым импорт `startOfYear`.

Альтернатива — брать последний элемент отсортированного массива — короче, но связывает корректность helper с внешним порядком. Изменение сортировки AccountsSnapshotsService отклонено: другие потребители могут ожидать новые снимки первыми. Отдельный MongoDB-запрос за одним снимком пока не нужен: исправление может использовать уже загружаемые данные без нового метода сервиса.

### Сохранить правила построения периодов

Существующие циклы построения месяцев и лет получают исправленную начальную дату. Явный `fromDate` сохраняет приоритет; `toDate`, категории, валютные buckets и пустые результаты сохраняют текущую семантику. Доступными считаются снимки, которые возвращает текущая пользовательская выборка, то есть не позднее текущего момента. История с будущими снимками не расширяет диапазон по умолчанию.

Альтернатива — определять начало по самой ранней операции — меняет смысл отчёта для счетов с начальным остатком без операций и выходит за согласованный контракт.

### Проверять диапазон и суммы на разных уровнях

Unit-тесты ReportsService фиксируют время, используют снимки разных лет и разных счетов в нескольких порядках и проверяют периоды и нижнюю границу агрегации. Покрыть отсутствие снимков, явные даты и обратный диапазон. HTTP-регрессия с реальной тестовой MongoDB создаёт личную историю прошлого года и сравнивает годовой доход с `/incomes/revenue` за точно совпадающие границы и валюту. Для HTTP-теста использовать прошлый год относительно текущего времени, избегая глобальной подмены часов MongoDB и JWT.

## Risks / Trade-offs

- [Ответы станут длиннее при большой истории] → Это ожидаемое восстановление исторических периодов; пагинация и ограничение истории не входят в исправление.
- [Случайное изменение других потребителей снимков] → Общий сервис и сортировку не менять; исправить выбор только в ReportsService.
- [Расхождение на границах часовых поясов] → Существующую календарную семантику не менять; проверять совпадающие фактические границы агрегации, использовать даты вдали от границы года для снимков.

## Migration Plan

Миграция данных не требуется. После регрессионных проверок и сборки изменение развёртывается обычным способом. Откат — возврат изменения ReportsService; сохранённые данные не затрагиваются.
