# Групповые финансы

Все маршруты ниже относительны к `/api/v1/groups/:groupId` и требуют JWT действующего участника. Семья и организация имеют одинаковые финансовые правила. Личные маршруты остаются личными; групповые операции не входят в личные расходы автора или указанного участника.

## Права

Владелец имеет все права. У нового/повторно вступившего участника все четыре финансовых права выключены. Владелец выдаёт непустое подмножество прав через `PATCH /members/:userId/permissions`, например:

```json
{"manageTransactions":true}
```

| Действие | Право |
| --- | --- |
| Создать/переименовать/архивировать/удалить неиспользованный счёт | manageAccounts |
| Создать/изменить/архивировать/удалить категорию | manageCategories |
| Создать/изменить/удалить лимит | manageLimits |
| Читать финансовые данные, вносить доходы, расходы и переводы | Любой действующий участник |
| Изменить/удалить расход | Владелец, действующий автор, участник расхода либо делегат manageTransactions |
| Изменить участника расхода | Владелец, действующий автор либо делегат manageTransactions |
| Изменить/удалить доход | Владелец, действующий автор либо делегат manageTransactions |
| Изменить/отменить перевод | Владелец, действующий автор либо делегат manageTransactions |
| Выдать права, управлять группой и приглашениями | Только владелец |

Права настроек не дают дополнительных прав на чужие операции. Выход/исключение сбрасывает права, повторное вступление их не восстанавливает. При передаче владения прежний владелец становится участником без делегированных прав. Проверки используют текущее состояние базы, а не сведения в JWT.

manageTransactions независимо от трёх прав настроек: оно не разрешает управлять счетами/категориями/лимитами, группой или приглашениями. Ответ PATCH всегда содержит четыре boolean, непереданные права сохраняются; null/строки/числа, неизвестные поля и пустой запрос — 400. Свои эффективные права возвращаются прямо в [DTO группы](groups-api.md#группа-и-эффективные-права); искать себя в каталоге участников не требуется. Клиенты со строгой схемой должны принять четвёртое поле. Отсутствующее поле старого членства считается false, владельцу право доступно по роли.

## Кошелёк

`POST /accounts` создаёт отдельный именованный счёт группы, например `{"name":"Семейный","currency":"RUB","amount":1000,"openedAt":"2024-01-01T00:00:00Z"}`. name обязателен (1–100 символов после trim); currency обязателен, trim/uppercase, поддерживаемый валютный код. Валюта счёта неизменяема и не зависит от defaultCurrency участников. Начальная сумма неотрицательна, по умолчанию 0; дата открытия по умолчанию равна текущему времени. Создание группы само по себе счёт не создаёт. Необязательный type принимает balance/saving, по умолчанию balance. Несколько счетов одинакового типа, валюты и имени разрешены: повторный POST создаёт новый счёт с новым _id, а не возвращает 409. Группового defaultAccountId нет; каждая операция явно выбирает accountId.

`GET /accounts` возвращает массив активных и архивных счетов; optional type/currency фильтруют список (currency нормализуется trim/uppercase, неподдерживаемые значения — 400). `GET /accounts/:accountId` — счёт с текущим amount и последними месячными снимками timeline. До даты открытия баланс равен нулю. Снимки — кэш остатков на конец месяца UTC; в текущем месяце текущий amount может отличаться от снимка при будущих операциях.

`DELETE /accounts/:accountId` допустим только при нулевом начальном остатке и отсутствии истории операций, включая удалённые. Корректировка баланса выполняется доходом/расходом; прямого редактирования снимков группы нет. Накопления доступны как type=saving. Переводы между счетами одного бюджета доступны через `/transfers`; переводы между разными бюджетами недоступны.

`PATCH /accounts/:accountId` принимает только `{"name":"Общий резерв"}` и возвращает 200 с обновлённым DTO. name обязателен, 1–100 символов после trim; пустой PATCH, blank name, type/currency/amount/initialAmount/openedAt или неизвестные поля — 400. Переименование разрешено и архивному счёту, не меняет _id и деньги.

`POST /accounts/:accountId/archive` без полей body/query возвращает 204 и сохраняет archivedAt. Архивировать можно и счёт с ненулевым/отрицательным остатком или историей. Повторное архивирование — 404, восстановления нет. Чтение счёта, timeline, операций, revenue, лимитов и отчётов сохраняется. Новые доходы/расходы, любой PATCH или DELETE старой операции архивного счёта возвращают 404 при наличии обычных прав на неё — даже владельцу, автору и делегату. Деньги, снимки и историческая атрибуция не меняются. Пустой неиспользованный архивный счёт можно удалить по тем же правилам RESTRICT, что активный.

DTO счёта сохраняет `_id`, name, type, currency, archivedAt (null либо дата), initialAmount, openedAt, amount и timeline. Архивирование не является финансовой операцией и не обнуляет остаток. manageAccounts требуется для rename/archive, но не даёт права исправлять чужие доходы/расходы. Отзыв права действует с прежним JWT; счёт другого бюджета через маршрут своей группы — 404.

## Операции

```json
{
  "accountId":"<счёт группы>",
  "categoryId":"<категория группы>",
  "participantId":"<действующий участник>",
  "amount":150.50,
  "transactionDate":"2024-02-10T12:00:00Z",
  "description":"Продукты"
}
```

`POST /expenses` принимает этот объект. participantId необязателен, по умолчанию вызывающий пользователь. createdBy сервер назначает из JWT. Дополнительно поддерживаются merchant и items. Расход может быть внесён за другого участника. В ответе сохраняются createdBy и participantId.

`POST /incomes` принимает accountId, amount, transactionDate и необязательное description. У дохода нет participantId. Суммы положительны с точностью валюты счёта: JPY — 0, RUB/USD — 2, KWD — 3 знака. Например KWD 0.001 допустим, JPY 0.1 и RUB 0.001 возвращают 400 без изменения записи/баланса. Доход/расход наследует currency счёта; ответ содержит её, передавать currency при создании или PATCH операции нельзя (400). Эти правила применяются и при PATCH amount. Денежный price каждой позиции items проверяется по той же валюте; quantity положителен и может быть дробным. amount не обязан равняться сумме позиций. Дата операции не может быть раньше открытия кошелька. Расход может привести к отрицательному учётному остатку на balance и saving. Для активного saving доступны те же прямые доходы/расходы, precision, openedAt и правила author/participant, что для balance; операция меняет только выбранный счёт. Расходы saving входят в общий лимит категории/валюты. Для перемещения денег между счетами группы используется `/transfers`, без пары расход/доход.

`GET /expenses`, `GET /incomes`, `GET /transactions` возвращают `{items,total,page,limit}`. Поддерживаются accountId, fromDate, toDate, transactionType и currency; у расходов дополнительно categoryId и participantId. `GET /expenses/revenue` суммирует amount расходов с теми же фильтрами и возвращает `{"totalRevenue":0.001,"currencies":[{"currency":"KWD","totalRevenue":0.001}]}`. Верхний totalRevenue равен единственной валютной сумме, 0 при отсутствии записей, null при нескольких валютах; разные валюты не складываются. fromDate/toDate присутствуют, если заданы в запросе. Валютные корзины отсортированы по коду. currency в фильтрах нормализуется trim/uppercase; неподдерживаемый код — 400; другая поддерживаемая валюта даёт пустую выдачу и нулевой revenue. Фильтр participantId включает исторические расходы бывших участников и не означает фильтр автора.

`GET /expenses/:id`, `PATCH /expenses/:id`, `DELETE /expenses/:id` и аналогичные пути incomes работают с одной записью. PATCH расхода: amount, description, merchant, items, categoryId, participantId. PATCH дохода: amount, description. Счёт, автор и дата неизменяемы. При изменении иных полей разрешено сохранить прежнего бывшего участника или архивную категорию; новое назначение на них запрещено. Удаление логическое, повторное удаление — 404; компенсация баланса выполняется один раз.

Например, после выдачи manageTransactions супруга отправляет `PATCH /incomes/:id` с `{"amount":150,"description":"Исправленная сумма"}` для дохода мужа. Ответ 200 сохраняет прежний createdBy, возвращает amount=150; баланс меняется только на разницу с прежней суммой. `DELETE /incomes/:id` возвращает 204, исключает 150 из остатка и сохраняет супругу в deletedBy. То же правило действует для чужого расхода, с обратным знаком изменения баланса.

Делегат может менять participantId на действующего участника той же группы; чужой или бывший участник — 404 без изменения записи и денег. Авторство сохраняется, даже если автор вышел из группы. После отзыва manageTransactions чужая несвязанная операция возвращает 403 с тем же JWT; собственные операции и расходы, назначенные на пользователя, остаются доступны по обычным правилам. Любая операция другого бюджета через маршрут своей группы — 404; права в одной группе не дают доступ к другой или к личным данным.

## Авторы и участники в истории

Все ответы с групповой операцией — create/PATCH, детали, элементы списков расходов/доходов/переводов и `/transactions` — содержат `createdByActor`. Расход с сохранённым participantId также содержит `participantActor`; у дохода/перевода и legacy-расхода без participantId этого поля нет. Исходные createdBy/participantId сохраняются строками ObjectId, не заменяются объектами. DELETE сохраняет 204 без тела. Краткий объект имеет ровно четыре поля:

```json
{"userId":"<исходный идентификатор>","firstName":"Анна","lastName":null,"isAnonymized":false}
```

firstName и lastName — string либо null; отсутствующее поле профиля становится null, сохранённая пустая строка остаётся пустой. При расходе за другого человека createdByActor относится к автору, participantActor — к участнику расхода. При разрешённом PATCH participantId обновляется и participantActor; автор не меняется. Эти объекты вычисляет сервер: переданные клиентом actor-поля в create/PATCH дают 400.

Имена берутся из текущего активного профиля при новом запросе, включая бывшего или исключённого участника. После переименования история показывает новое имя, без снимка прежних персональных данных. Каталог `/members` по-прежнему содержит только действующих членов. Имя в истории не возвращает доступ бывшему участнику: запросы группы с его прежним JWT дают 404. Исторический фильтр participantId продолжает работать по идентификатору, включая архивный счёт.

Для deletion_pending, deleted или отсутствующего профиля возвращается:

```json
{"userId":"<тот же идентификатор>","firstName":null,"lastName":null,"isAnonymized":true}
```

Имена скрываются уже после принятого запроса удаления, до очистки профиля worker. isAnonymized не различает причины отсутствия имени и не раскрывает статус удаления. Подпись «Удалённый пользователь» выбирает фронт. Запрос, начавшийся до изменения профиля, может видеть ранее прочитанное состояние; следующий запрос после изменения получает актуальный результат. Сервер не кеширует и не сохраняет копии имён. Фронту следует обновлять свою историю после смены профиля/удаления.

Resolver получает ID только из операций выбранной страницы уже доступной группы. Новый каталог пользователей или endpoint по произвольным ID не появляется; пустой participantId-фильтр не раскрывает имя постороннего человека. В actor нет email, description, auth-полей, настроек валюты или личных финансов. Сбой чтения профилей даёт нормализованную серверную ошибку, а не ложное успешное обезличивание. В create/PATCH lookup выполняется в той же транзакции: ошибка откатывает операцию и деньги. Личные DTO, revenue и отчёты не обогащаются. Клиенты со строгими схемами должны принять новые поля; миграций и изменений сохранённых операций нет.

## Переводы между счетами группы

`POST /transfers` возвращает 201. Пример тела для RUB → USD:

```json
{
  "sourceAccountId":"<RUB-счёт группы>",
  "destinationAccountId":"<USD-счёт группы>",
  "sourceAmount":90000,
  "destinationAmount":1000,
  "transactionDate":"2025-02-15T12:00:00Z",
  "description":"Пополнение резерва"
}
```

Оба счёта должны быть различными, активными и принадлежать этой группе; дата не раньше openedAt каждой стороны. Поддерживаются balance ↔ saving, balance ↔ balance и saving ↔ saving. Личный счёт или счёт другой группы возвращает 404, даже если вызывающий владеет обоими бюджетами. Несуществующая запись и недействующее членство также дают 404; отсутствие JWT — 401.

Обе суммы обязательны, положительны после нормализации и соответствуют точности валюты своей стороны (JPY — 0, RUB/USD — 2, KWD — 3 знака). В одной валюте суммы должны совпадать. Валюты, ownerType/ownerId и createdBy назначает сервер; participantId не принимается. Некорректная сумма/дата/неизвестное поле — 400 без изменений. Комиссий и внешнего курса нет.

Ответ сохраняет `_id`, type=transfer, ownerType/ownerId, createdBy, transactionDate, description и две стороны `source`/`destination` с accountId, snapshotId, amount и currency. Верхнего amount/currency и participantId нет. Дополнительно возвращается `effectiveRate`: `{"baseCurrency":"RUB","quoteCurrency":"USD","rate":0.011111111111111112}` — destination.amount / source.amount. Направление всегда от source к destination; для одной валюты rate=1. Общая история возвращает ту же форму перевода.

При создании исходного остатка на transactionDate должно хватать на sourceAmount; будущий доход не покрывает прошлое списание. При PATCH увеличения достаточно остатка на ту же дату для дополнительного списания с учётом прежнего перевода. Недостаток — 400; точная граница допустима. Уменьшение и изменение только description не требуют нового покрытия. Обычные групповые доходы/расходы сохраняют прежнюю политику отрицательного остатка.

`PATCH /transfers/:id` возвращает 200 и принимает только sourceAmount, destinationAmount, description (до 1000 символов). Для одной валюты при изменении суммы нужно передать обе одинаковые суммы. Счета, валюты и дата неизменяемы. Пустой объект, null, нулевая/отрицательная сумма, неверная точность или неизвестные поля — 400. Изменять/отменять перевод может действующий автор, владелец либо manageTransactions; чужой перевод без этих прав — 403. Права настроек не дают прав на чужие переводы. После выхода автора createdBy сохраняется, доступ теряется; отзыв проверяется с прежним JWT.

`DELETE /transfers/:id` возвращает 204 и логически удаляет перевод, записывая deletedBy. Компенсируются обе стороны; достаточность destination не проверяется, поэтому после расходования зачисления отмена может оставить его отрицательным. Архив любой стороны блокирует create/PATCH/DELETE с 404 при наличии прав, включая изменение description. История архивных счетов читается. Любой перевод, включая удалённый, блокирует удаление каждого связанного счёта (RESTRICT). Общий маршрут удаления transactions не позволяет обойти правила перевода.

Повторный POST — отдельный перевод с новым _id, если средств хватает; ключа идемпотентности нет. Повторный DELETE — 404 без повторной компенсации. Оба денежных эффекта, запись и пересчёт последующих месячных снимков выполняются атомарно; ошибка откатывает всё. Конкурентные операции и изменения членства/прав/архива сериализуются.

`GET /transfers` возвращает `{items,total,page,limit}`, `GET /transfers/:id` — одну запись. Фильтры списка: accountId, currency, fromDate/toDate, page/limit. Архивный accountId допустим; чужой — 404, обратный период/неподдерживаемая валюта — 400. В общей истории `/transactions` поддерживается transactionType=transfer. accountId совпадает с любой стороной; currency — с валютой любой стороны. Разные фильтры соединяются AND и могут совпасть с разными сторонами: исходный accountId + валюта destination включает перевод. Период включителен; порядок transactionDate DESC, _id DESC. Одна запись появляется один раз. `/expenses`, revenue и использование лимитов не включают переводы.

В отчёте движения суммируются по валюте каждой стороны, независимо от типа счёта и category-filter. Пример RUB balance с opening=1000 → RUB saving=100: balance=900, saving=100, transfersIn=100, transfersOut=100, incomes=expenses=0. Для RUB90000 → USD1000 списание RUB90000 и зачисление USD1000 остаются разными корзинами. Внутри balance или saving обе суммы движения видны, остаток типа не удваивается. Архив не исключает историю; отменённый перевод не входит в движения и ledger.

Этап 05 не требует миграции или reset: используются существующие Transfer и денежные стороны. Seeds дополнены реальным переводом USD1000. Откат к этапу 04 при наличии групповых переводов потребует отдельного плана: прежний ledger и отчёты не учитывают их эффекты. Рабочая база и развёрнутый API этим change не изменялись.

## Категории, лимиты, отчёты

- `/expense-categories`: GET и POST; `/:id`: GET, PATCH, DELETE. Поля name (1–100 после trim), description, color; PATCH также принимает isArchived. Имя уникально внутри бюджета. Категорию со ссылками из операций/лимитов удалить нельзя; архивирование сохраняет историю, запрещая новые назначения.
- `/expense-limits`: GET и POST; `/:id`: GET, PATCH, DELETE. Создание принимает categoryId, обязательную currency, total с точностью валюты, startDate/endDate (по умолчанию текущий месяц UTC). PATCH принимает total/startDate/endDate. GET списка поддерживает categoryId/periodDate/currency. currency неизменяема через PATCH (400), возвращается в DTO. Пересекающиеся включительные периоды одной категории и валюты — 409, разные валюты допускаются. Валюта лимита может пока не иметь счёта группы. В ответе сохраняется rest (без новых aliases used/remaining): rest = total − расходы той же категории/валюты за период; при отсутствии расходов rest равен total. Некорректная точность total — 400 без изменения данных. rest учитывает всех участников и может стать отрицательным; лимит не блокирует расходы.
- `/reports/months`, `/reports/years`: GET, fromDate/toDate и categories (массив либо строка ObjectId через запятую). Возвращают массив `{ period, currencies: [...] }`, согласованный с денежной структурой личных отчётов; старого плоского варианта нет. Поля корзины показаны ниже; balance суммирует balance-счета, saving — saving-счета; transfersIn/transfersOut содержат зачисления/списания переводов в валюте соответствующей стороны, saves отсутствует. Категории фильтруют расходы; balance и saving остаются полными остатками счетов соответствующих типов. participantId и currency не поддерживаются в query отчёта с общим балансом — используйте список/сумму расходов.

Пример элемента месячного отчёта (начальный остаток KWD 0.001, доход 0.002):

```json
{
  "period": "2024-02",
  "currencies": [{
    "currency": "KWD",
    "incomes": 0.002,
    "expenses": 0,
    "transfersIn": 0,
    "transfersOut": 0,
    "balance": 0.003,
    "saving": 0,
    "expensesByCategory": []
  }]
}
```

Корзины отсортированы по коду валюты; расходы по категориям имеют форму `{ categoryId, total }`, включая нулевые суммы выбранных категорий. Пустая группа возвращает периоды с `currencies: []`. Счёт без движений всё равно даёт валютную корзину, до openedAt её balance/saving равны 0. Отчёт использует полные UTC-месяцы/годы (`YYYY-MM`/`YYYY`), даже если указана часть периода. По умолчанию диапазон — с 1 января текущего UTC-года до сейчас; обратный диапазон или диапазон более 100 лет — 400. Остаток включает opening и все активные операции предыдущих периодов. categories ограничивает только расходы/разбивку, доходы и остатки balance/saving полные; чужая категория — 404. Архивные категории и расходы бывших участников остаются в отчётах, удалённые операции исключаются.

Временные границы групповых отчётов и лимитов используют UTC. Выход участника не меняет историю/суммы. После удаления группы её финансовые данные сохраняются, но все соответствующие маршруты становятся недоступными.

## Ошибки и эксплуатация

Создание возвращает 201, чтение/изменение — 200, групповое удаление — 204. Некорректные/неизвестные поля и пустой PATCH — 400; без JWT — 401; недостаточно прав действующего участника — 403; недоступная группа/объект — 404; конфликт состояния — 409. Сбой финансовой транзакции — 503. Изменения записи и баланса атомарны, в том числе при конкуренции с отзывом прав или исключением.

Развёртывание требует MongoDB replica set. Для валютного этапа подтверждены только dev-данные: миграция не предусмотрена. Перед переходом нужны чистые или пересозданные dev-данные с явными валютами; старые суммы не получают валюту из профиля пользователя. При обнаружении реальных данных требуется отдельный план отображения валют и миграции до развёртывания. Mongoose создаёт индексы из актуальных схем. Для локальной ручной проверки используйте [development seed](group-finances-seed.md).

Проверки: `npm run test`, `npm run test:e2e -- --runInBand`, `npm run build`. E2E используют временный локальный mongod replica set; путь к бинарнику можно задать MONGOD_BINARY. Тесты не подключаются к рабочей базе.

Обновление разрешений не требует миграции финансовых данных или новых секретов. При откате приложения делегаты теряют новые полномочия; сохранённое поле можно оставить. Перед повторным включением проверить сохранённые назначения, при необходимости явно отозвать их. История финансов и старый аудит сохраняются.


Переход этапа 03 ломает прежний групповой контракт: фронтенд одновременно добавляет name/currency при создании счёта, currency при создании лимита и читает currencies в отчётах. В disposable dev-базе штатный `NODE_ENV=development npm run seed` очищает коллекции и создаёт обновлённые fixtures; не применять к данным, которые надо сохранить. Откат backend/frontend требует пересоздания dev-данных под прежний контракт: старый fixed2 код не сохраняет точность KWD 0.001. Ни purge, ни seed рабочей базы автоматически не выполняются.


После этапа 04 общий отчёт включает активные и архивные счета. Пример: RUB balance с opening 100, второй RUB balance 20 и RUB saving с opening 50, доходом 10 и расходом 5 дают balance=120, saving=55, incomes=10, expenses=5. Накопления не входят повторно в balance; opening и archive не создают доход/расход. KWD saving 0.001 образует отдельную валютную корзину. Архивирование и category-filter не убирают сохранённые накопления из отчёта.

Для этапа 04 миграция/reset данных не нужны: существующий счёт сохраняется как balance. Seeds дополнены вторым balance и saving. Откат к этапу 03 после создания новых счетов/архива не сохраняет семантику: прежняя версия показывает saving=0 и не блокирует архивные мутации. В disposable dev-среде используйте fixtures соответствующей версии; сохранение реальных данных при откате требует отдельного плана.
