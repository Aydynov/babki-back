# Группы и приглашения

Группа (`family` или `organization`) объединяет пользователей, каждый из которых может участвовать в нескольких группах. Доступны членство, приглашения и [групповые финансы](group-finances-api.md): счета и накопления, доходы, расходы, переводы, категории, лимиты, планы, долги и отчёты. Личные финансовые API остаются независимыми.

Все маршруты ниже требуют `Authorization: Bearer <JWT>` и начинаются с настроенного API-префикса (по умолчанию `/api/v1`). Пользователь запроса определяется JWT. Создатель группы становится её владельцем.

| Метод и путь                                    | Тело                                                            | Результат                                           |
| ----------------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------- |
| POST `/groups`                                  | `{"name":"Семья","type":"family","description":"Общий бюджет"}` | 201, группа                                         |
| GET `/groups`                                   | —                                                               | 200, собственные группы                             |
| GET `/groups/:id`                               | —                                                               | 200, группа                                         |
| PATCH `/groups/:id`                             | `{"name":"Новое название"}`                                     | 200, группа; только владелец                        |
| DELETE `/groups/:id`                            | —                                                               | 204; только владелец                                |
| GET `/groups/:id/members`                       | —                                                               | 200, действующие участники                          |
| PATCH `/groups/:id/members/:userId/permissions` | `{"manageTransactions":true}`                                   | 200, полный набор прав; только владелец             |
| POST `/groups/:id/leave`                        | `{}`                                                            | 204; владелец сначала передаёт владение             |
| DELETE `/groups/:id/members/:userId`            | —                                                               | 204; только владелец, нельзя исключить себя         |
| POST `/groups/:id/ownership`                    | `{"userId":"идентификатор участника"}`                          | 200, группа; только владелец                        |
| POST `/groups/:id/invitations`                  | `{}`                                                            | 201, `{id,token,expiresAt}`; только владелец        |
| GET `/groups/:id/invitations`                   | —                                                               | 200, метаданные без токенов; только владелец        |
| DELETE `/groups/:id/invitations/:invitationId`  | —                                                               | 204; только владелец                                |
| POST `/group-invitations/preview`               | `{"token":"полученный токен"}`                                  | 200, только `{name,type,expiresAt}`, без вступления |
| POST `/group-invitations/accept`                | `{"token":"полученный токен"}`                                  | 200, `{groupId,role:"member"}`                      |

Списки принимают `page` и `limit`, возвращают `{items,total,page,limit}`. Название после trim — 1–100 символов, описание — до 1000. Тип обязателен при создании и неизменяемый; пустая строка очищает описание. Неизвестные поля, null-описание и пустой PATCH отклоняются.

## Группа и эффективные права

Каждый ответ с группой (создание, элементы списка, детали, изменение и передача владения) содержит `permissions` вызывающего пользователя. Ответ передачи владения относится к прежнему владельцу: после успешной передачи его role — member, все четыре права — false. Каталог участников для получения своих прав не нужен.

Пример DTO владельца; даты и идентификаторы иллюстративны:

```json
{
  "id": "670000000000000000000001",
  "name": "Семья",
  "type": "family",
  "ownerId": "670000000000000000000002",
  "role": "owner",
  "permissions": {
    "manageAccounts": true,
    "manageCategories": true,
    "manageLimits": true,
    "manageTransactions": true
  },
  "createdAt": "2026-10-17T09:00:00.000Z",
  "updatedAt": "2026-10-17T09:00:00.000Z"
}
```

У обычного участника role — member, ownerId по-прежнему указывает владельца группы. У нового/повторно вступившего участника permissions:

```json
{
  "manageAccounts": false,
  "manageCategories": false,
  "manageLimits": false,
  "manageTransactions": false
}
```

Владелец независимо делегирует четыре права: manageAccounts — счета, manageCategories — категории, manageLimits — лимиты, manageTransactions — изменение/удаление любых доходов и расходов и переназначение участника расхода. Непереданные поля PATCH сохраняют прежнее значение. Например, `{"manageTransactions":true}` возвращает при остальных выключенных правах:

```json
{
  "manageAccounts": false,
  "manageCategories": false,
  "manageLimits": false,
  "manageTransactions": true
}
```

Делегат не получает управление группой, приглашениями, членством, владением или выдачей прав. Участники могут читать финансовые данные и создавать операции без делегирования. Полная [матрица финансового доступа](group-finances-api.md#права).

Пустой PATCH, неизвестное поле, null, строка или число вместо boolean дают 400. Изменение прав владельца — 409, недействующий получатель — 404, попытка делегирования обычным участником — 403. Выдача/отзыв и сброс прав сохраняют аудит; выход, исключение и передача владения сбрасывают делегирование. Изменение действует с прежним JWT; permissions в уже полученном ответе может устареть, сервер проверяет каждую мутацию заново.

Клиенты со строгими схемами ответов должны принимать новое поле permissions в группе и manageTransactions в полном объекте прав, включая каталог участников и ответ PATCH. В старых членствах без manageTransactions оно считается false для участника; у владельца все права эффективны автоматически. Массовая миграция и автоматическая выдача нового права не требуются; ранее записанные события аудита не переписываются.

## Приглашение на клиенте

Backend возвращает секрет только при создании приглашения. Клиент формирует ссылку на собственный экран, например `https://your-app.example/join#token=<token>`. Fragment не отправляется серверу страницы. Не помещайте токен в URL API или query-параметры и не записывайте его в аналитику/логи.

Получатель авторизуется либо регистрируется, вызывает `POST /api/v1/group-invitations/preview` с токеном только в JSON body и видит текущие название/тип группы и срок ссылки. Preview требует JWT, но не членство. Пример ответа 200 с `Cache-Control: no-store`:

```json
{ "name": "Семья", "type": "family", "expiresAt": "2026-10-24T09:00:00.000Z" }
```

Это все поля preview: идентификаторов группы/ссылки, имени приглашающего, участников, прав, описания и финансов нет. type принимает family/organization; expiresAt — ISO-дата срока приглашения, а не новый срок. Query, неизвестные поля, отсутствие token, null и неверный формат (ровно 43 символа base64url) дают 400. Без действительного JWT — 401. Неизвестный, истёкший (включая now=expiresAt), использованный, отозванный токен или удалённая группа дают одинаковый 400 `Invalid invitation`, без причины и сведений о группе. Сбой чтения — нормализованный 503.

Preview не потребляет и не продлевает ссылку, не меняет членство/аудит/группу/финансы и не открывает обычное чтение группы. Повторный preview допустим в пределах лимита. Владелец и действующий участник тоже могут получить preview 200; собственный accept сохраняет 409 и не потребляет ссылку. Успешный preview ничего не резервирует: до accept ссылку могут отозвать, использовать, она может истечь или группа может быть удалена; последующий accept заново проверяет состояние и возвращает общий 400.

После preview получатель явно подтверждает вступление. Клиент передаёт токен в JSON body запроса `POST /api/v1/group-invitations/accept`. Само открытие ссылки ничего не меняет. Frontend должен сохранять токен на время авторизации безопасным для своего приложения способом и удалять его после использования.

Ссылка не привязана к email: первый успешно вступивший получатель потребляет её. Срок — 7 суток, владелец может отозвать ссылку. Действующий участник получает 409 без потребления ссылки; повторное использование принятой ссылки возвращает 400. Токен в базе хранится только как SHA-256 digest.

На preview и accept действует **суммарный** общий между экземплярами сервиса лимит 10 запросов на пользователя за фиксированное минутное окно, включая успешные запросы и невалидные тела до DTO-validation. Например, девять preview и один accept исчерпывают квоту. Превышение возвращает 429 и положительный `Retry-After`; после следующей минуты квота обновляется. Не опрашивайте preview циклически. Другой пользователь имеет свою квоту; запрос без JWT даёт 401 и не расходует персональный счётчик. Сбой хранилища лимита возвращает 503 до чтения приглашения. Это единственная запись при preview.

Токен и digest не возвращаются из preview/accept и не записываются приложением в логи. Для путей этих двух маршрутов query целиком исключается из request logs и error.path, включая 401/400/429/503; ошибочно переданный query не служит источником token. Ошибки DTO-validation этих маршрутов возвращают общее сообщение `Invalid invitation request`, чтобы не повторять секрет, ошибочно использованный как имя неизвестного поля. Ошибки доступности действительного по формату токена сохраняют `Invalid invitation`. Клиент всё равно должен передавать секрет только в body: инфраструктурные proxy/APM логи настраиваются отдельно.

## Доступ и история

Чужая, удалённая или покинутая группа возвращает 404. Действующий участник без необходимой роли получает 403. Владелец не может выйти до передачи владения; передача самому себе и попытка исключить владельца возвращают 409. Невалидная, истёкшая, отозванная или использованная ссылка возвращает общий 400.

Групповые финансовые операции возвращают краткие createdByActor/participantActor с текущими именами, включая вышедших участников; исходные идентификаторы сохраняются. deletion_pending/deleted и отсутствующий профиль дают null-имена и isAnonymized=true. Это дополнение финансовых DTO, а не расширение каталога действующих членов. Подробный [контракт исторических субъектов](group-finances-api.md#авторы-и-участники-в-истории).

Выход и исключение действуют сразу для новых запросов, даже со старым JWT. Повторное вступление требует нового действующего приглашения и сохраняет историю. Удаление группы логическое: сохраняются идентификатор и события членства, прекращается доступ и принятие ссылок. Публичного восстановления и чтения архива нет.

## Развёртывание и откат

MongoDB должен работать как replica set, поскольку создание, приглашения, членство и передача владения используют транзакции. При запуске `GroupsModule.onModuleInit` последовательно вызывает `createIndexes()` для пяти новых моделей и дожидается результата до открытия HTTP-порта. Повторный запуск безопасен: существующие эквивалентные индексы не пересоздаются и не удаляются. Ошибка создания индекса останавливает запуск; сервисному пользователю БД нужны права создания коллекций и индексов.

Уникальны пары группа–пользователь и пользователь–минутное окно, а также digest приглашения. TTL применяется только к старым счётчикам лимита. Истечение приглашения проверяется в запросе, а не фоновым удалением.

Новые секреты, переменные окружения и миграции существующих данных не нужны. Перед включением проверить создание группы двумя тестовыми пользователями, приглашение, передачу владения и удаление. На уровне прокси/APM не журналировать тела создания/предпросмотра/принятия приглашений и секрет в ответе создания.

Откат: развернуть прежнюю версию приложения, сохранив новые коллекции. Это убирает маршруты, но не уничтожает историю и сведения об использованных приглашениях. Повторное включение продолжит работать с сохранённым состоянием.

## Проверки

Установите совместимый `mongod`, доступный в PATH, либо задайте `MONGOD_BINARY=/absolute/path/to/mongod`. Все e2e-наборы запускают собственный временный односерверный replica set на свободном loopback-порту. Они не используют рабочую базу: при завершении процесс останавливается, временная директория и тестовые секреты удаляются. Нужны разрешения на запуск локального процесса и локальные TCP-сокеты.

```sh
npm run test -- --runInBand groups
npm run test:e2e -- --runInBand test/groups.e2e-spec.ts test/groups-concurrency.e2e-spec.ts
npm run test -- --runInBand
npm run test:e2e -- --runInBand
npm run build
openspec validate --specs --no-interactive
```

Конкурентные тесты удерживают первую настоящую транзакцию после записи группы, запускают конкурента и затем освобождают первую. Проверяются одноразовость, взаимные гонки принятия/отзыва/удаления и передачи/выхода/исключения, а также откат при ошибке записи события. Транзакции и операции MongoDB не подменяются моками.

## Совместные планы

Групповые планы используют существующий Plan/PlansService: create/read доступны действующим участникам, PATCH/close/archive/delete — действующему автору, владельцу или `manageTransactions`. Удаление группы закрывает все маршруты планов, сохраняя Plan и expense origin. Удаление автора очищает его личные планы, сохраняя групповые с обезличенным createdByActor. Подробный контракт, маршруты и ошибки: [групповые планы](group-finances-api.md#планы-покупок-этап-08). До включения этих маршрутов нужен отдельный owner backfill старых личных Plan, описанный в [rollout](entity-deletion-rollout.md#владельцы-планов-этап-08).

## Совместные долги

`/groups/:groupId/debts` и вложенные `/repayments` используют общие Debt/DebtTransaction. Только долги перед группой; создание не двигает деньги. Управление и отмена проверяют автора **долга**, owner/manageTransactions, а не автора repayment. Выход/удаление автора сохраняет историю, group deletion закрывает маршруты. Контракт: [долги перед группой](group-finances-api.md#долги-перед-группой-этап-09). Перед включением нужен отдельный [owner backfill долгов](entity-deletion-rollout.md#владельцы-долгов-этап-09); личные маршруты/ручные remaining/status сохраняются.

## Формы списков и интеграционный маршрут

Группы и приглашения используют `id`, финансовые документы — `_id`; это намеренно сохранённый контракт. Списки `/groups`, `/groups/:id/members`, `/groups/:id/invitations` имеют `{items,total,page,limit}`, defaults page1/limit20, limit≤100. Группы и приглашения сортируются createdAt ASC/_id ASC, участники — joinedAt ASC/_id ASC. Группа имеет optional description (может отсутствовать); остальные публичные поля приведены в примере выше. Member: `{userId,firstName?,lastName?,role,joinedAt,permissions}`. Invitation list item: `{id,createdBy,createdAt,expiresAt,status}`, optional acceptedBy/acceptedAt после принятия и revokedBy/revokedAt после отзыва, без token/digest; status pending/accepted/revoked/expired. Создание приглашения возвращает только `{id,token,expiresAt}`, preview — только `{name,type,expiresAt}`, accept — только `{groupId,role}`. Финансовые списки имеют собственные формы, описанные в [справочнике](group-finances-api.md#справочник-форм-ответов-и-параметров).

Полный семейный маршрут и матрица §1–10 — [финальная сверка](family-budget-contract-audit.md). В нём пользователи с личными USD/EUR видят одинаковую семью RUB/USD, отдельно от личных счетов и второй группы; проверены создание/исполнение планов, погашение/отмена долгов и история после выхода/удаления. Эти локальные HTTP-тесты не являются проверкой browser frontend или уже развёрнутого API. Актуальные команды: `npm run test:e2e -- --runInBand test/family-budget-contract.e2e-spec.ts` и `openspec validate --specs --no-interactive`; исходный change групп уже архивирован.
