## Сквозной сценарий и независимые денежные ожидания

Запуск: `npm run test:e2e -- --runInBand test/family-budget-contract.e2e-spec.ts`. Helper принимает необязательные личные валюты, defaults других suites остаются USD. В новом сценарии супруги имеют USD/EUR, личные счета по37 и независимую вторую группу с EUR71. Все права/членство и финансы меняются через HTTP; lifecycle удаления использует существующие UserDeletionService/Worker без sleep.

Семья: RUB balance1000 + saving100, USD balance50. RUB доход200, расход50, перевод100 в резерв; план100 исполнен новым расходом120; долг200 погашен financial60/noncash20, дополнительный financial10 отменён. Проверены точные origin/expenseId/incomeId и отсутствие движения при создании плана/долга и noncash. Январь2024 UTC:

| RUB показатель             |  Ожидание |
| -------------------------- | --------: |
| balance                    |       990 |
| saving                     |       200 |
| incomes                    |       260 |
| expenses                   |       170 |
| transfersIn / transfersOut | 100 / 100 |
| remaining долга            |       120 |
| rest лимита500             |       330 |

USD остаётся отдельной корзиной balance50 и нулевыми движениями. Итоги сравниваются для обоих супругов. Личные бюджеты и вторая группа не меняются; чужие accountId дают404. Отзыв прав действует со старым JWT, выход закрывает доступ. Владелец видит текущее имя бывшего участника; pending и завершённый worker дают null-имена без изменения групповых денег и ссылок. После удаления личного пользователя сравниваются только доступные оставшемуся пользователю бюджеты.

Предметные suites сохраняют более широкое покрытие: minor units JPY/KWD, валютные лимиты, отрицательные остатки, достаточность перевода, future/backdated и UTC, архивы, RESTRICT, ошибки I/O/rollback и обе последовательности конкурентных операций с отзывом прав/выходом/архивом. Эти проверки не дублируются в одном длинном сценарии.

Они используют только disposable DB. Инструкции реального rollout остаются в существующем документе: replica set, backup/остановка writes, готовность индексов, разбор issues и повторный audit. Достоверная валюта реальных старых групповых сумм требует отдельного плана; из профиля участника её не выводят.

Фронтенд отвечает за переключатель бюджета, cache keys, сохранение приглашения на время входа, возврат после регистрации и закрытие форм. Не добавлялись cross-budget transfers, общий default account, атомарное создание group+wallet, публичный preview, новые роли или конвертация валют. Эти решения не считаются открытыми backend gaps в согласованном объёме.

## Найденный блокер и его отдельное устранение

Первый HTTP-прогон этапа10 остановился на выдаче внутреннего mutationVersion в account DTO; присутствовал __v во вложенных ответах. Независимое ревью подтвердило проблему и арифметику. По согласованию пользователя создан отдельный [hide-group-financial-internal-fields](../openspec/changes/archive/2026-10-18-hide-group-financial-internal-fields/proposal.md): единый interceptor рекурсивно скрывает metadata на трёх групповых финансовых controllers. Он переиспользует обход personalResponse с разными наборами ключей; личный набор исключений сохранён, БД/locks/сервисные результаты не меняются.

Regression `group-financial-response` падал на mutationVersion до исправления. После исправления targeted unit: 2 suites/4 tests passed; два новых HTTP suites: 2/2 passed, 8.803s. Проверки secret/internal fields не ослаблялись: добавлен также запрет __v. В JWT-ошибке уточнено существующее error="Error"; формат API не менялся. Старый неуспешный прогон не считается итоговым результатом.
