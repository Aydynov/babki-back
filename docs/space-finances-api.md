Все финансовые маршруты ниже относительны к `/api/v1/spaces/:spaceId` и требуют JWT действующего участника. Данные видны всем участникам. Финансовые ответы содержат spaceId.

# Пространственные финансы

## Права

Владелец имеет все права. У нового/повторно вступившего участника все четыре финансовых права выключены. Владелец выдаёт непустое подмножество прав через `PATCH /members/:userId/permissions`, например:

```json
{ "manageTransactions": true }
```

| Действие                                                         | Право                                                                         |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Создать/переименовать/архивировать/удалить неиспользованный счёт | manageAccounts                                                                |
| Создать/изменить/архивировать/удалить категорию                  | manageCategories                                                              |
| Создать/изменить/удалить лимит                                   | manageLimits                                                                  |
| Читать финансовые данные, вносить доходы, расходы и переводы     | Любой действующий участник                                                    |
| Изменить/удалить расход                                          | Владелец, действующий автор, участник расхода либо делегат manageTransactions |
| Изменить участника расхода                                       | Владелец, действующий автор либо делегат manageTransactions                   |
| Изменить/удалить обычный доход (не погашение долга)              | Владелец, действующий автор либо делегат manageTransactions                   |
| Изменить/отменить перевод                                        | Владелец, действующий автор либо делегат manageTransactions                   |
| Выдать права, управлять пространствой и приглашениями                  | Только владелец                                                               |

Права настроек не дают дополнительных прав на чужие операции. Выход/исключение сбрасывает права, повторное вступление их не восстанавливает. При передаче владения прежний владелец становится участником без делегированных прав. Проверки используют текущее состояние базы, а не сведения в JWT.

manageTransactions независимо от трёх прав настроек: оно не разрешает управлять счетами/категориями/лимитами, пространствой или приглашениями. Ответ PATCH всегда содержит четыре boolean, непереданные права сохраняются; null/строки/числа, неизвестные поля и пустой запрос — 400. Свои эффективные права возвращаются прямо в [DTO пространства](spaces-api.md#пространство-и-эффективные-права); искать себя в каталоге участников не требуется. Клиенты со строгой схемой должны принять четвёртое поле. Отсутствующее поле старого членства считается false, владельцу право доступно по роли.

## Кошелёк

`GET /accounts` возвращает массив активных и архивных счетов; optional type/currency фильтруют список (currency нормализуется trim/uppercase, неподдерживаемые значения — 400). `GET /accounts/:accountId` — счёт с amount на конец текущего месяца UTC и последними месячными снимками timeline. amount включает все операции текущего месяца, в том числе с будущей датой, и не включает операции последующих месяцев. Если дата открытия позже конца текущего месяца, баланс равен нулю. Те же правила действуют для amount в ответах создания и переименования счёта. Снимки — кэш остатков на конец месяца UTC.

`DELETE /accounts/:accountId` допустим только при нулевом начальном остатке и отсутствии истории операций, включая удалённые. Корректировка баланса выполняется доходом/расходом; прямого редактирования снимков пространства нет. Накопления доступны как type=saving. Переводы между счетами одного бюджета доступны через `/transfers`; переводы между разными бюджетами недоступны.

`PATCH /accounts/:accountId` принимает только `{"name":"Общий резерв"}` и возвращает 200 с обновлённым DTO. name обязателен, 1–100 символов после trim; пустой PATCH, blank name, type/currency/amount/initialAmount/openedAt или неизвестные поля — 400. Переименование разрешено и архивному счёту, не меняет _id и деньги.

`POST /accounts/:accountId/archive` без полей body/query возвращает 204 и сохраняет archivedAt. Архивировать можно и счёт с ненулевым/отрицательным остатком или историей. Повторное архивирование — 404, восстановления нет. Чтение счёта, timeline, операций, revenue, лимитов и отчётов сохраняется. Новые доходы/расходы, любой PATCH или DELETE старой операции архивного счёта возвращают 404 при наличии обычных прав на неё — даже владельцу, автору и делегату. Деньги, снимки и историческая атрибуция не меняются. Пустой неиспользованный архивный счёт можно удалить по тем же правилам RESTRICT, что активный.

DTO счёта сохраняет `_id`, name, type, currency, archivedAt (null либо дата), initialAmount, openedAt, amount и timeline. Архивирование не является финансовой операцией и не обнуляет остаток. manageAccounts требуется для rename/archive, но не даёт права исправлять чужие доходы/расходы. Отзыв права действует с прежним JWT; счёт другого бюджета через маршрут своего пространства — 404.

## Операции

```json
{
  "accountId": "<счёт пространства>",
  "categoryId": "<категория пространства>",
  "participantId": "<действующий участник>",
  "amount": 150.5,
  "transactionDate": "2024-02-10T12:00:00Z",
  "description": "Продукты"
}
```

`POST /expenses` принимает этот объект. participantId необязателен, по умолчанию вызывающий пользователь. createdBy сервер назначает из JWT. Дополнительно поддерживаются merchant и items. Расход может быть внесён за другого участника. В ответе сохраняются createdBy и participantId.

`POST /incomes` принимает accountId, amount, transactionDate и необязательное description. У дохода нет participantId. Суммы положительны с точностью валюты счёта: JPY — 0, RUB/USD — 2, KWD — 3 знака. Например KWD 0.001 допустим, JPY 0.1 и RUB 0.001 возвращают 400 без изменения записи/баланса. Доход/расход наследует currency счёта; ответ содержит её, передавать currency при создании или PATCH операции нельзя (400). Эти правила применяются и при PATCH amount. Денежный price каждой позиции items проверяется по той же валюте; quantity положителен и может быть дробным. amount не обязан равняться сумме позиций. Дата операции не может быть раньше открытия кошелька. Расход может привести к отрицательному учётному остатку на balance и saving. Для активного saving доступны те же прямые доходы/расходы, precision, openedAt и правила author/participant, что для balance; операция меняет только выбранный счёт. Расходы saving входят в общий лимит категории/валюты. Для перемещения денег между счетами пространства используется `/transfers`, без пары расход/доход.

`GET /expenses`, `GET /incomes`, `GET /transactions` возвращают `{items,total,page,limit}`. Поддерживаются accountId, fromDate, toDate, transactionType и currency; у расходов дополнительно categoryId и participantId. `GET /expenses/revenue` суммирует amount расходов с теми же фильтрами и возвращает `{"totalRevenue":0.001,"currencies":[{"currency":"KWD","totalRevenue":0.001}]}`. Верхний totalRevenue равен единственной валютной сумме, 0 при отсутствии записей, null при нескольких валютах; разные валюты не складываются. fromDate/toDate присутствуют, если заданы в запросе. Валютные корзины отсортированы по коду. currency в фильтрах нормализуется trim/uppercase; неподдерживаемый код — 400; другая поддерживаемая валюта даёт пустую выдачу и нулевой revenue. Фильтр participantId включает исторические расходы бывших участников и не означает фильтр автора.

`GET /expenses/:id`, `PATCH /expenses/:id`, `DELETE /expenses/:id` и аналогичные пути incomes работают с одной записью. PATCH расхода: amount, description, merchant, items, categoryId, participantId. PATCH дохода: amount, description. Счёт, автор и дата неизменяемы. При изменении иных полей разрешено сохранить прежнего бывшего участника или архивную категорию; новое назначение на них запрещено. Удаление логическое, повторное удаление — 404; компенсация баланса выполняется один раз.

Например, после выдачи manageTransactions супруга отправляет `PATCH /incomes/:id` с `{"amount":150,"description":"Исправленная сумма"}` для дохода мужа. Ответ 200 сохраняет прежний createdBy, возвращает amount=150; баланс меняется только на разницу с прежней суммой. `DELETE /incomes/:id` возвращает 204, исключает 150 из остатка и сохраняет супругу в deletedBy. То же правило действует для чужого расхода, с обратным знаком изменения баланса.

Делегат может менять participantId на действующего участника того же пространства; чужой или бывший участник — 404 без изменения записи и денег. Авторство сохраняется, даже если автор вышел из пространства. После отзыва manageTransactions чужая несвязанная операция возвращает 403 с тем же JWT; собственные операции и расходы, назначенные на пользователя, остаются доступны по обычным правилам. Любая операция другого бюджета через маршрут своего пространства — 404; права в одном пространстве не дают доступ к другому пространству.

## Авторы и участники в истории

```json
{
  "userId": "<исходный идентификатор>",
  "firstName": "Анна",
  "lastName": null,
  "isAnonymized": false
}
```

firstName и lastName — string либо null; отсутствующее поле профиля становится null, сохранённая пустая строка остаётся пустой. При расходе за другого человека createdByActor относится к автору, participantActor — к участнику расхода. При разрешённом PATCH participantId обновляется и participantActor; автор не меняется. Эти объекты вычисляет сервер: переданные клиентом actor-поля в create/PATCH дают 400.

Имена берутся из текущего активного профиля при новом запросе, включая бывшего или исключённого участника. После переименования история показывает новое имя, без снимка прежних персональных данных. Каталог `/members` по-прежнему содержит только действующих членов. Имя в истории не возвращает доступ бывшему участнику: запросы пространства с его прежним JWT дают 404. Исторический фильтр participantId продолжает работать по идентификатору, включая архивный счёт.

Для deletion_pending, deleted или отсутствующего профиля возвращается:

```json
{
  "userId": "<тот же идентификатор>",
  "firstName": null,
  "lastName": null,
  "isAnonymized": true
}
```

Имена скрываются уже после принятого запроса удаления, до очистки профиля worker. isAnonymized не различает причины отсутствия имени и не раскрывает статус удаления. Подпись «Удалённый пользователь» выбирает фронт. Запрос, начавшийся до изменения профиля, может видеть ранее прочитанное состояние; следующий запрос после изменения получает актуальный результат. Сервер не кеширует и не сохраняет копии имён. Фронту следует обновлять свою историю после смены профиля/удаления.

Resolver получает ID только из операций выбранной страницы уже доступного пространства. Новый каталог пользователей или endpoint по произвольным ID не появляется; пустой participantId-фильтр не раскрывает имя постороннего человека. В actor нет email, description, auth-полей, настроек валюты или личных финансов. Сбой чтения профилей даёт нормализованную серверную ошибку, а не ложное успешное обезличивание. В create/PATCH lookup выполняется в той же транзакции: ошибка откатывает операцию и деньги. Клиенты со строгими схемами должны принять новые поля; миграций и изменений сохранённых операций нет.

## Переводы между счетами пространства

`POST /transfers` возвращает 201. Пример тела для RUB → USD:

```json
{
  "sourceAccountId": "<RUB-счёт пространства>",
  "destinationAccountId": "<USD-счёт пространства>",
  "sourceAmount": 90000,
  "destinationAmount": 1000,
  "transactionDate": "2025-02-15T12:00:00Z",
  "description": "Пополнение резерва"
}
```

Оба счёта должны быть различными, активными и принадлежать этому пространству; дата не раньше openedAt каждой стороны. Поддерживаются balance ↔ saving, balance ↔ balance и saving ↔ saving. Счёт другого пространства возвращает 404, даже если вызывающий владеет обоими бюджетами. Несуществующая запись и недействующее членство также дают 404; отсутствие JWT — 401.

При создании исходного остатка на transactionDate должно хватать на sourceAmount; будущий доход не покрывает прошлое списание. При PATCH увеличения достаточно остатка на ту же дату для дополнительного списания с учётом прежнего перевода. Недостаток — 400; точная граница допустима. Уменьшение и изменение только description не требуют нового покрытия. Обычные пространственные доходы/расходы сохраняют прежнюю политику отрицательного остатка.

`PATCH /transfers/:id` возвращает 200 и принимает только sourceAmount, destinationAmount, description (до 1000 символов). Для одной валюты при изменении суммы нужно передать обе одинаковые суммы. Счета, валюты и дата неизменяемы. Пустой объект, null, нулевая/отрицательная сумма, неверная точность или неизвестные поля — 400. Изменять/отменять перевод может действующий автор, владелец либо manageTransactions; чужой перевод без этих прав — 403. Права настроек не дают прав на чужие переводы. После выхода автора createdBy сохраняется, доступ теряется; отзыв проверяется с прежним JWT.

`DELETE /transfers/:id` возвращает 204 и логически удаляет перевод, записывая deletedBy. Компенсируются обе стороны; достаточность destination не проверяется, поэтому после расходования зачисления отмена может оставить его отрицательным. Архив любой стороны блокирует create/PATCH/DELETE с 404 при наличии прав, включая изменение description. История архивных счетов читается. Любой перевод, включая удалённый, блокирует удаление каждого связанного счёта (RESTRICT). Общий маршрут удаления transactions не позволяет обойти правила перевода.

Повторный POST — отдельный перевод с новым _id, если средств хватает; ключа идемпотентности нет. Повторный DELETE — 404 без повторной компенсации. Оба денежных эффекта, запись и пересчёт последующих месячных снимков выполняются атомарно; ошибка откатывает всё. Конкурентные операции и изменения членства/прав/архива сериализуются.

`GET /transfers` возвращает `{items,total,page,limit}`, `GET /transfers/:id` — одну запись. Фильтры списка: accountId, currency, fromDate/toDate, page/limit. Архивный accountId допустим; чужой — 404, обратный период/неподдерживаемая валюта — 400. В общей истории `/transactions` поддерживается transactionType=transfer. accountId совпадает с любой стороной; currency — с валютой любой стороны. Разные фильтры соединяются AND и могут совпасть с разными сторонами: исходный accountId + валюта destination включает перевод. Период включителен; порядок transactionDate DESC, _id DESC. Одна запись появляется один раз. `/expenses`, revenue и использование лимитов не включают переводы.

В отчёте движения суммируются по валюте каждой стороны, независимо от типа счёта и category-filter. Пример RUB balance с opening=1000 → RUB saving=100: balance=900, saving=100, transfersIn=100, transfersOut=100, incomes=expenses=0. Для RUB90000 → USD1000 списание RUB90000 и зачисление USD1000 остаются разными корзинами. Внутри balance или saving обе суммы движения видны, остаток типа не удваивается. Архив не исключает историю; отменённый перевод не входит в движения и ledger.

Этап 05 не требует миграции или reset: используются существующие Transfer и денежные стороны. Seeds дополнены реальным переводом USD1000. Откат к этапу 04 при наличии пространственных переводов потребует отдельного плана: прежний ledger и отчёты не учитывают их эффекты. Рабочая база и развёрнутый API этим change не изменялись.

## Категории, лимиты, отчёты

- `/expense-categories`: GET и POST; `/:id`: GET, PATCH, DELETE. Поля name (1–100 после trim), description, color; PATCH также принимает isArchived. Имя уникально внутри бюджета. Категорию со ссылками из операций/лимитов удалить нельзя; архивирование сохраняет историю, запрещая новые назначения.
- `/expense-limits`: GET и POST; `/:id`: GET, PATCH, DELETE. Создание принимает categoryId, обязательную currency, total с точностью валюты, startDate/endDate (по умолчанию текущий месяц UTC). PATCH принимает total/startDate/endDate. GET списка поддерживает categoryId/periodDate/currency. currency неизменяема через PATCH (400), возвращается в DTO. Пересекающиеся включительные периоды одной категории и валюты — 409, разные валюты допускаются. Валюта лимита может пока не иметь счёта пространства. В ответе сохраняется rest (без новых aliases used/remaining): rest = total − расходы той же категории/валюты за период; при отсутствии расходов rest равен total. Некорректная точность total — 400 без изменения данных. rest учитывает всех участников и может стать отрицательным; лимит не блокирует расходы.
- `/reports/months`, `/reports/years`: GET, fromDate/toDate и categories (массив либо строка ObjectId через запятую). Возвращают массив `{ period, currencies: [...] }`, с независимыми валютными корзинами; старого плоского варианта нет. Поля корзины показаны ниже; balance суммирует balance-счета, saving — saving-счета; transfersIn/transfersOut содержат зачисления/списания переводов в валюте соответствующей стороны, saves отсутствует. Категории фильтруют расходы; balance и saving остаются полными остатками счетов соответствующих типов. participantId и currency не поддерживаются в query отчёта с общим балансом — используйте список/сумму расходов.

Пример элемента месячного отчёта (начальный остаток KWD 0.001, доход 0.002):

```json
{
  "period": "2024-02",
  "currencies": [
    {
      "currency": "KWD",
      "incomes": 0.002,
      "expenses": 0,
      "transfersIn": 0,
      "transfersOut": 0,
      "balance": 0.003,
      "saving": 0,
      "expensesByCategory": []
    }
  ]
}
```

Корзины отсортированы по коду валюты; расходы по категориям имеют форму `{ categoryId, total }`, включая нулевые суммы выбранных категорий. Пустая пространство возвращает периоды с `currencies: []`. Счёт без движений всё равно даёт валютную корзину, до openedAt её balance/saving равны 0. Отчёт использует полные UTC-месяцы/годы (`YYYY-MM`/`YYYY`), даже если указана часть периода. По умолчанию диапазон — с 1 января текущего UTC-года до сейчас; обратный диапазон или диапазон более 100 лет — 400. Остаток включает opening и все активные операции предыдущих периодов. categories ограничивает только расходы/разбивку, доходы и остатки balance/saving полные; чужая категория — 404. Архивные категории и расходы бывших участников остаются в отчётах, удалённые операции исключаются.

Временные границы пространственных отчётов и лимитов используют UTC. Выход участника не меняет историю/суммы. После удаления пространства её финансовые данные сохраняются, но все соответствующие маршруты становятся недоступными.

## Ошибки и эксплуатация

Создание возвращает 201, чтение/изменение — 200, пространствовое удаление — 204. Некорректные/неизвестные поля и пустой PATCH — 400; без JWT — 401; недостаточно прав действующего участника — 403; недоступная пространство/объект — 404; конфликт состояния — 409. Сбой финансовой транзакции — 503. Изменения записи и баланса атомарны, в том числе при конкуренции с отзывом прав или исключением.

Развёртывание требует MongoDB replica set. Для валютного этапа подтверждены только dev-данные: миграция не предусмотрена. Перед переходом нужны чистые или пересозданные dev-данные с явными валютами; старые суммы не получают валюту из профиля пользователя. При обнаружении реальных данных требуется отдельный план отображения валют и миграции до развёртывания. Mongoose создаёт индексы из актуальных схем. Для локальной ручной проверки используйте [development seed](space-finances-seed.md).

Проверки: `npm run test`, `npm run test:e2e -- --runInBand`, `npm run build`. E2E используют временный локальный mongod replica set; путь к бинарнику можно задать MONGOD_BINARY. Тесты не подключаются к рабочей базе.

Обновление разрешений не требует миграции финансовых данных или новых секретов. При откате приложения делегаты теряют новые полномочия; сохранённое поле можно оставить. Перед повторным включением проверить сохранённые назначения, при необходимости явно отозвать их. История финансов и старый аудит сохраняются.

Переход этапа 03 ломает прежний пространственный контракт: фронтенд одновременно добавляет name/currency при создании счёта, currency при создании лимита и читает currencies в отчётах. В disposable dev-базе штатный `NODE_ENV=development npm run seed` очищает коллекции и создаёт обновлённые fixtures; не применять к данным, которые надо сохранить. Откат backend/frontend требует пересоздания dev-данных под прежний контракт: старый fixed2 код не сохраняет точность KWD 0.001. Ни purge, ни seed рабочей базы автоматически не выполняются.

После этапа 04 общий отчёт включает активные и архивные счета. Пример: RUB balance с opening 100, второй RUB balance 20 и RUB saving с opening 50, доходом 10 и расходом 5 дают balance=120, saving=55, incomes=10, expenses=5. Накопления не входят повторно в balance; opening и archive не создают доход/расход. KWD saving 0.001 образует отдельную валютную корзину. Архивирование и category-filter не убирают сохранённые накопления из отчёта.

Для этапа 04 миграция/reset данных не нужны: существующий счёт сохраняется как balance. Seeds дополнены вторым balance и saving. Откат к этапу 03 после создания новых счетов/архива не сохраняет семантику: прежняя версия показывает saving=0 и не блокирует архивные мутации. В disposable dev-среде используйте fixtures соответствующей версии; сохранение реальных данных при откате требует отдельного плана.

## Планы покупок (этап 08)

План принадлежит бюджету пространства, автор назначается из JWT. Любой действующий участник создаёт и читает планы; изменяет, исполняет, архивирует и удаляет действующий автор, владелец или `manageTransactions`. Права настроек сами по себе не разрешают изменять чужой план. Plan не резервирует деньги и до исполнения не является расходом: не меняет счета, снимки, отчёты, revenue или использование лимитов.

| Метод  | Путь                 | Результат                                            |
| ------ | -------------------- | ---------------------------------------------------- |
| POST   | `/plans`             | 201, новый план                                      |
| GET    | `/plans`             | 200, `{ items, total, page, limit }`                 |
| GET    | `/plans/:id`         | 200, включая архивный план                           |
| PATCH  | `/plans/:id`         | 200, активный неархивный план                        |
| DELETE | `/plans/:id`         | 204, физическое удаление активного плана без расхода |
| POST   | `/plans/:id/archive` | 204, архивирование                                   |
| POST   | `/plans/:id/close`   | 201, закрытый план                                   |

Create требует `description` (trim, 1–500), `targetDate` (строгая ISO-дата, прошлое допустимо), положительную `amount`, `currency` (trim/uppercase, поддерживаемая валюта) и активную `categoryId` этой пространства. Минимальные суммы: JPY 1, RUB 0.01, KWD 0.001; лишние десятичные разряды дают 400. PATCH принимает только description/targetDate/amount/categoryId; пустое тело, null, внутренние поля и смена валюты дают 400. Чужая категория — 404, новое назначение архивной — 409; правка других полей сохраняет прежнюю архивную категорию.

List принимает `status=active|closed`, `currency`, `includeArchived=true|false`, `page`, `limit`. По умолчанию архив исключён; `true` включает обе пространства записей, `false` действительно исключает архив. Порядок: targetDate ASC, createdAt DESC, _id DESC. Детали архива доступны участникам, но PATCH/close дают 404, DELETE — 409; повторный archive — 404. Закрытый PATCH даёт 400, DELETE — 409. Повторный DELETE уже удалённого активного плана — 404. Восстановления нет.

### Полное однократное исполнение

`POST /plans/:id/close` принимает обязательный `accountId`, необязательные `amount`, `closingDate`, `description`, `participantId`. По умолчанию сумма/описание берутся из плана, дата — сейчас, участник расхода — исполнитель. Плановая amount не меняется; фактическая находится в обычном расходе по expenseId. closedAt — серверное время закрытия, closingDate — дата расхода, targetDate не ограничивает исполнение.

Например, план USD 100 можно исполнить за USD 120. План остаётся amount=100/status=closed, счёт уменьшается на 120, ровно один расход amount=120 имеет `origin: { type: "plan", id: "<planId>" }`, createdBy исполнителя и выбранного действующего participantId. Этот расход один раз учитывается в отчёте, revenue и лимите своей категории/валюты. Dev fixture демонстрирует план 1000/расход 1200, увеличивающий food expenses с 8450.5 до 9650.5 и уменьшающий rest лимита с 41549.5 до 40349.5; активный план 2000 не влияет на эти суммы.

Счёт должен быть активным, того же пространства и валюты, дата — не раньше openedAt; категория плана — активной. Чужой/архивный счёт или недействующий участник — 404, другая валюта/ранняя дата/точность — 400, архивная категория — 409. Как обычный пространственный расход, исполнение допускает отрицательный остаток. Повторный close — 400 без второго расхода. Передача expenseId, частичное исполнение, reopen и отдельная отмена не поддерживаются.

Права на созданный расход проверяются независимо: автор плана не получает права на чужой расход только из-за плана. Обычные PATCH/DELETE расхода исправляют/компенсируют фактический учёт, сохраняя Plan.amount/status=closed/expenseId и origin расхода. После soft-delete обычное чтение расхода даёт 404, план сохраняет историческую связь и не исполняется снова. Архив счёта блокирует изменение/удаление расхода; архив плана сам расход не меняет. Любой active/closed/archived план защищает категорию от удаления (409).

Проверки членства/полномочий, создание расхода, effects, закрытие плана и подготовка actor-ответа входят в одну ClientSession с пространственный сериализацией. Неожиданная ошибка записи/actor lookup возвращает 503 и откатывает план, расход, счета и снимки. Гонки закрытия, архива, удаления ссылок и отзыва прав эквивалентны последовательному исполнению. Без JWT — 401, недоступный бюджет/план — 404, недостаточные права действующего участника — 403.

## Долги перед пространствой (этап 09)

Поддерживается только «нам должны». Создание долга не выдаёт деньги и не создаёт расход; principal и remaining первоначально равны, status=active. Финансовое погашение создаёт доход пространства, некассовое уменьшает долг без движения денег.

Любой действующий участник создаёт/читает долг и историю. Изменение, погашение, отмена, архив и удаление доступны действующему автору **долга**, владельцу или manageTransactions. Автор погашения фиксируется отдельно, но дополнительных прав не получает. После отзыва делегирования прежний исполнитель чужого долга не может отменить свою запись; settings-only этого не разрешает.

| Метод  | Путь                                        | Результат                                        |
| ------ | ------------------------------------------- | ------------------------------------------------ |
| POST   | `/debts`                                    | 201 Debt                                         |
| GET    | `/debts`                                    | 200 `{ items, total, page, limit }`              |
| GET    | `/debts/:id`                                | 200, включая архивный долг                       |
| PATCH  | `/debts/:id`                                | 200 Debt                                         |
| DELETE | `/debts/:id`                                | 204 без истории/доходов и архива; повтор 404     |
| POST   | `/debts/:id/archive`                        | 204; повтор 404                                  |
| POST   | `/debts/:id/repayments`                     | 201 `{ debt, repayment }`                        |
| GET    | `/debts/:id/repayments`                     | 200 пагинированная история, включая отменённые   |
| GET    | `/debts/:id/repayments/:repaymentId`        | 200, включая отменённую запись/архивный родитель |
| POST   | `/debts/:id/repayments/:repaymentId/cancel` | 200 `{ debt, repayment }`; повтор 409            |

Create: debtor (trim 1–150), principalAmount (положительная, конечная и точной валютной размерности), currency (trim/uppercase), optional description (trim до 150), dueDate (строгая ISO-дата). JPY 1, RUB 0.01 и KWD 0.001 принимаются; лишние разряды, нулевые/отрицательные суммы дают 400. Нет direction, accountId, remainingAmount или status на входе. PATCH принимает только debtor/description/dueDate/principalAmount; пустой PATCH и неизвестные/внутренние поля — 400. dueDate=null очищает срок, description='' очищает описание; null остальных полей — 400.

До первой записи истории principal можно изменить, remaining изменяется вместе с ним. После любой истории, даже полностью отменённой, principal PATCH даёт 409. У closed неархивного долга можно редактировать metadata; remaining/status вручную не меняются. Полное погашение закрывает долг, отмена открывает его снова. Отдельных close/reopen и space transactions-алиаса истории нет.

### Погашение и отмена

POST repayment требует amount, repaymentDate и **явный boolean isIncome**. Строки `"false"`/`"true"`, числа и null не принимаются. При true нужен активный accountId своего пространства и валюты; дата не раньше openedAt. При false accountId запрещён. Optional description до 1000; default — `Погашение долга <debtor>`. Просроченный dueDate и дата до создания самого долга не мешают погашению; для financial действует открытие счёта. Переплата, точность, закрытый долг — 400; чужой/архивный счёт — 404; несовпадение валюты — 400. Остаток меняется на amount, ноль закрывает долг. Повтор POST создаёт отдельную запись при достаточном remaining, ключа идемпотентности нет.

Например, долг USD 100 погашается финансово на 40: remaining=60, один income40 увеличивает счёт/доходы отчёта, история сохраняет точный incomeId, доход — `origin: { type: "debt", id: "<debtId>" }`. Затем noncash60 закрывает долг, но не меняет счёт/доходы. Отмена первого погашения восстанавливает remaining40/status=active, помечает income удалённым и возвращает деньги к состоянию без него. Переплата61 при remaining60 отклоняется без записи. Расходы, expense revenue и лимиты не изменяются из-за погашения.

Исправление — только cancel и новая запись. Cancel сохраняет исходную сумму/дату/incomeId/origin, фиксирует cancelledAt/By и компенсирует доход на **исходную дату**. Некассовая отмена меняет только долг/историю. Уже потраченный доход может привести к отрицательному пространственному cash, как обычная компенсация дохода. Future income и его отмена влияют на будущие снимки/отчёты, не на текущий остаток. Несогласованный/отсутствующий/уже удалённый income — 409; повтор отмены — 409 без второй компенсации. Клиент не передаёт incomeId, автора или сумму отмены.

Обычные PATCH amount/description и DELETE связанного space income запрещены с 409 после обычных income-прав и проверки активного счёта. Архивный счёт сохраняет приоритет 404. Автор дохода после отзыва прав на чужой долг получает 409 на обычном income API и 403 на debt cancellation; автор долга может отменить доход другого исполнителя по правам долга.

Архив долга запрещает PATCH/repay/cancel с 404, сохраняет чтение истории и деньги. Любая история, включая отменённую, origin-доход или архив запрещают физический DELETE долга с 409. Архив счёта запрещает financial repay/cancel, но не noncash при неархивном долге. Soft-deleted income сохраняет account RESTRICT. Удаление пространства закрывает маршруты, удаление автора сохраняет долг/историю с обезличенным actor. Actor профили разрешаются одним batch на страницу/составной ответ; cancelledByActor следует той же политике pending/deleted/missing.

Групповая сериализация охватывает актуальные права, debt/history, доход/компенсацию, remaining/status и подготовку actor-ответа в одной ClientSession. Неожиданная ошибка записи/ответа — 503 с полным rollback, включая снимки и версии. Конкурентные погашения не превышают remaining, повторные отмены не удваивают компенсацию. Без JWT — 401, недоступный объект — 404, недостаточные полномочия участника — 403.

## Справочник форм ответов и параметров

Обозначения ниже: ID — строка ObjectId, date — ISO string в ответе JSON, `?` — поле может отсутствовать, `T|null` — поле присутствует со значением или null. `optional` во входном DTO не разрешает null автоматически. Поля владельца/автора назначает сервер; передача внутренних полей клиентом отклоняется. Числовые денежные поля используют точность валюты; отрицательные amount в ответе счёта допустимы. Архивное поле не заменяет status плана/долга.

Origin — `{type:"plan"|"debt",id:ID}`, у обычной новой операции — null. Объект Actor имеет **ровно** `{userId,firstName:string|null,lastName:string|null,isAnonymized:boolean}`. Финансовые DTO содержат spaceId; actor.userId обозначает человека. Space.ownerId является административным владельцем. Политика исключения служебных полей описана выше. Мягко удалённые операции не возвращаются в обычных списках; история погашений сохраняет отменённые записи.

| GET список                          | Параметры и форма                                                                                       | Порядок                                                       |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `/accounts`                         | optional `type,currency`; массив Account, без pagination, архивные включены                             | для пространства стабильный порядок не гарантирован                 |
| `/expense-categories`               | без query; массив Category, включая архивные                                                            | createdAt DESC; порядок одинаковых timestamps не гарантирован |
| `/expense-limits`                   | optional `categoryId,currency,periodDate`; массив Limit                                                 | startDate DESC, tie-break не гарантирован                     |
| `/transactions`, `/incomes`         | `page,limit,accountId,fromDate,toDate,transactionType,currency`; `{items,total,page,limit}`             | transactionDate DESC, _id DESC                                |
| `/expenses`                         | те же параметры плюс `categoryId,participantId`; страница                                               | transactionDate DESC, _id DESC                                |
| `/transfers`                        | `page,limit,accountId,fromDate,toDate,currency`; страница                                               | transactionDate DESC, _id DESC                                |
| `/plans`                            | `page,limit,status,currency,includeArchived`; страница                                                  | targetDate ASC, createdAt DESC, _id DESC                      |
| `/debts`                            | `page,limit,status,currency,includeArchived`; страница                                                  | createdAt DESC, _id DESC                                      |
| `/debts/:id/repayments`             | `page,limit`; страница, включая cancelled                                                               | transactionDate DESC, createdAt DESC, _id DESC                |
| `/expenses/revenue`                 | фильтры расходов; `{totalRevenue:number\|null,currencies:[{currency,totalRevenue}],fromDate?,toDate?}`  | currencies ASC                                                |
| `/reports/months`, `/reports/years` | `fromDate,toDate,categories` (comma-separated IDs); массив `{period,currencies:[CurrencyPeriodReport]}` | периоды ASC, currencies ASC                                   |

Pagination: page по умолчанию1, limit20, page≥1, limit1…100; total — полное количество подходящих записей, пустая страница имеет items=[] без исчезновения metadata. У разных маршрутов форма списка различается: нельзя оборачивать массив счетов/категорий/лимитов или отчётов в выдуманный page DTO. includeArchived принимает строки `true`/`false`, отсутствие эквивалентно false; значения `1`, `yes`, пустая строка отклоняются. Detail plans/debts читает архив независимо от фильтра списка. Валютные фильтры trim/uppercase; id-параметры валидируются как ObjectId.

Пример минимального запроса создания долга и последующего финансового погашения (ID — значения своего пространства):

```json
{ "debtor": "Заёмщик", "principalAmount": 200, "currency": "RUB" }
```

```json
{
  "amount": 60,
  "repaymentDate": "2024-01-06T12:00:00Z",
  "isIncome": true,
  "accountId": "670000000000000000000010"
}
```

Первый запрос возвращает 201 Debt с remainingAmount=200/status=active; второй — 201 `{debt,repayment}` с remainingAmount=140, repayment.isIncome=true и точным incomeId. Для noncash передают isIncome=false **без** accountId; incomeId отсутствует. Cancel без body/query возвращает тот же compound shape с cancelledAt/By/Actor и восстановленным остатком; повтор409. `PATCH /debts/:id {"dueDate":null}` очищает срок, а `{"description":""}` очищает описание; это не универсальная политика null для остальных DTO.

Методы CRUD: для income/expense/category/limit — POST коллекции201, GET списка/деталей200, PATCH деталей200, DELETE деталей204. Account дополнительно имеет POST `/:id/archive`204 и PATCH только name; Plan — POST close201 и archive204; Debt — repayments201/cancel200/archive204; Transfer — POST201, GET/PATCH200, DELETE204. Для ошибок состояния/прав используйте предметные разделы: статус DELETE204 не означает, что сущность с историей удаляема. Архив категории задаётся PATCH isArchived, а не отдельным маршрутом.

Все ошибки нормализует общий filter. Пример неизвестного currency во входе income (400):

```json
{
  "statusCode": 400,
  "message": ["property currency should not exist"],
  "error": "Bad Request",
  "path": "/api/v1/spaces/670000000000000000000001/incomes",
  "timestamp": "2026-10-18T08:00:00.000Z"
}
```

Поля error/path/timestamp присутствуют и при 401/403/404/409/503; message бывает string или string[]. Не определяйте поведение по одному error: при отсутствии JWT он равен `"Error"`, при обычном ForbiddenException — `"Forbidden"`. Основной машинный признак — statusCode/HTTP status. Приглашения имеют отдельное редактирование сообщений/path, no-store и квоту429 с Retry-After, как описано в spaces-api. Нормализованный 503 финансового сервисного сбоя не заменяет ошибки валидации400 или конфликты409.
