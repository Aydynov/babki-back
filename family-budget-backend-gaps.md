# Пробелы API бэка для семейного бюджета

Дата исследования: 2026-10-15.

Цель: супруги совместно управляют семейными финансами, сохраняя отдельные личные бюджеты.
Фронт позволяет выбрать личный бюджет или одну из своих групп.

Это список **предстоящих доработок**, а не отчёт об исправлениях и не согласованная спецификация.
Текущее состояние проверено чтением локального `../babki-back`; работа развёрнутого API не проверялась.
Предлагаемые имена полей и маршруты ниже требуют согласования с окончательным контрактом бэка.

## Приоритеты

| Приоритет | Пробел | Влияние |
| --- | --- | --- |
| P0 | Нет валюты группового бюджета и финансовых ответов | Нельзя достоверно подписать денежные значения |
| P0 | Нельзя делегировать управление всеми финансовыми операциями | Супруги не получают равное управление финансами |
| P1 | Групповые отчёты отличаются от личных | Текущие схемы и виджеты фронта не принимают ответы |
| P1 | Только один основной кошелёк, нет накоплений | Нельзя полноценно учитывать семейные счета и резервы |
| P1 | Нет групповых переводов | Нельзя перемещать деньги между семейными счетами |
| P1 | Нет групповых планов | Нельзя совместно планировать и исполнять будущие расходы |
| P1 | Нет групповых долгов | Нельзя совместно учитывать долги и погашения |
| P1 | Нет предпросмотра приглашения | До вступления нельзя подтвердить, в какую группу приглашают |
| P2 | Права текущего пользователя доступны только через список участников | Для управления интерфейсом нужно дополнительное чтение списка |
| P2 | Нет разрешения исторических участников в финансовой истории | После выхода человека его имя нельзя надёжно получить через каталог |
| P2 | Документация групп не отражает полностью текущее состояние | Фронт вынужден сверять документацию с реализацией |

P0 блокирует достоверный учёт или целевой сценарий равного управления. P1 нужен для полного
семейного бюджета с перечисленными возможностями. P2 улучшает контракт и удобство интеграции.
Для ограниченного первого релиза часть P1 можно отложить явным решением.

## 1. Валюта групповых финансов

**Подтверждено:** `CreateGroupAccountDto` принимает только `amount` и `openedAt`.
`GroupWalletService` не назначает кошельку валюту и название. У группы также нет валюты.
Создание групповых доходов и расходов не назначает валюту операции; лимиты и сводки не возвращают
явную валютную семантику. Денежные проверки группового API используют фиксированные два знака.

На фронте `Account` требует `currency` и `name`, а денежные значения форматируются по явно заданной
валюте. Личная `defaultCurrency` участника не определяет валюту семьи: супруги могут иметь разные настройки.

**Предлагаемая доработка:**

- Явно выбрать модель: одна валюта на группу или несколько валют через счета.
- Для сближения с личным бюджетом предпочтительны счета с неизменяемой валютой; даже единственный
  кошелёк должен иметь явную валюту в запросе создания и ответе.
- Возвращать валюту операций, лимитов и денежных сводок либо однозначно описать её получение
  из контекста. Для самостоятельных DTO предпочтительна явная валюта.
- Проверять точность сумм по валюте, согласовать её неизменяемость и совместимость связанных сущностей.
- Определить назначение валюты уже существующим групповым данным; не угадывать её на фронте.
- Опубликовать примеры ответов и ошибок несовместимой валюты.

**Приёмка:** два участника с разными личными валютами видят одинаковую валюту семейных денег;
в разных валютах не появляется общий арифметический итог без явно согласованной конвертации.

## 2. Равное управление финансовыми операциями

**Подтверждено:** в группе один владелец. Делегируются только `manageAccounts`, `manageCategories`
и `manageLimits`. Участник может изменять и удалять свои доходы, а расходы — свои или назначенные
на него. Переназначать участника расхода может владелец или автор. Делегированные права настроек
не дают права управлять чужими операциями.

Это не обеспечивает полное равенство супругов в управлении бюджетом.

**Предлагаемая доработка:** отдельное делегируемое право управления всеми финансовыми операциями
группы либо роль финансового администратора. Единственного владельца можно сохранить для управления
жизненным циклом группы. Название и гранулярность новых прав ещё не выбраны.

Нужно определить:

- Кто изменяет и удаляет чужие доходы, расходы и переводы, переназначает участника расхода.
- Кто управляет общими планами, долгами и их исполнением/погашением.
- Отделены ли приглашения, исключение участников, передача владения и удаление группы от финансовых прав.
- Как выдаются права после вступления; сейчас у нового участника все права настроек выключены.
- Как права сбрасываются при выходе, повторном вступлении и передаче владения.

**Приёмка:** уполномоченная супруга может исправить внесённые супругом финансовые записи, оставаясь
участницей; отзыв права действует с тем же JWT. Административные права не возникают неявно.

## 3. Единый контракт отчётов и финансовых DTO

**Подтверждено:** личный отчёт возвращает `{ period, currencies: [...] }`, включая `currency`,
`transfersIn`, `transfersOut`, `saving`. Групповой возвращает плоские `expenses`, `incomes`, `saves`,
`saving`, `balance`, `expensesByCategory`, без валюты; `saves` и `saving` всегда равны нулю.

Групповой баланс может быть отрицательным, тогда как текущая схема личного счёта на фронте требует
`amount >= 0`. Это допустимое правило группового учёта, а не ошибка бэка; фронт должен его поддержать.
Идентификаторы групп возвращаются как `id`, финансовые документы — преимущественно как `_id`.
Различие можно адаптировать на фронте, но его следует явно описать.

**Предлагаемая доработка:**

- Согласовать групповые отчёты с валютными корзинами личных отчётов.
- Зафиксировать формулы остатка, накоплений и переводов, включая отсутствие двойного учёта.
- После добавления накоплений заменить постоянные нули реальными расчётами.
- Описать DTO счетов, истории, операций и лимитов: обязательные поля, nullable/optional, идентификаторы,
  владельца бюджета и автора действия. Не обязательно менять все идентификаторы ради единообразия.
- Сохранить и документировать UTC-границы периодов, начальный остаток и операции до даты открытия.
- Не применять фильтр участника к общему балансу без отдельного определения смысла такой метрики.
  Сейчас фильтр есть у списка/суммы расходов, но отсутствует у групповых отчётов — это не дефект само по себе.

**Приёмка:** личный и групповой отчёты имеют согласованную денежную структуру; смена бюджета
не требует подстановки выдуманной валюты или финансовых показателей.

## 4. Несколько семейных счетов и накопления

**Подтверждено:** групповой API создаёт один основной кошелёк `balance`; повторное создание возвращает
409. Групповой `saving` не поддержан. Нет групповых маршрутов переименования и архивирования счёта.
Удаление допустимо только для кошелька без начального остатка и любой истории.

**Предлагаемая доработка:**

- Поддержать несколько именованных семейных счетов типов `balance` и `saving` с явной валютой.
- Определить создание, чтение, переименование, архивирование и удаление неиспользованного счёта.
- Сохранить историю архивных счетов и запретить новые операции по ним.
- Определить разрешённые операции со сберегательным счётом и способ его пополнения/изъятия.
- Отражать накопления и их движения в истории и отчётах без дублирования доходов/расходов.
- Если нужен счёт по умолчанию, хранить его в контексте группы, отдельно от личного `defaultAccountId`.

**Приёмка:** оба супруга видят общий резерв, могут пополнить и использовать его в рамках прав;
архивирование счёта не уничтожает финансовую историю.

## 5. Переводы

**Подтверждено:** у `GroupFinancesController` нет API переводов; групповой список операций допускает
только типы `income` и `expense`. Личный API переводов не является разрешением на групповые операции.

**Предлагаемая доработка:**

- Добавить переводы между счетами одной группы, включая `balance` и `saving`.
- Описать создание, чтение, редактирование, отмену/удаление, права и отражение в общей истории.
- Атомарно изменять оба остатка; повторная отмена не должна повторно компенсировать баланс.
- Для разных валют явно задавать исходящую и входящую суммы и правила точности.
- Отделить переводы от доходов/расходов в отчётности.

**Отдельное продуктовое решение:** переводы между личным и семейным бюджетами. Это полезно для
взноса в семейный бюджет, но текущим API не поддерживается и не должно возникать автоматически
из поддержки внутригрупповых переводов. Нужны проверки доступа к обоим бюджетам, правила видимости
для остальных участников, согласованное отображение взноса и защита от двойного учёта.

**Приёмка:** перевод внутри семьи не увеличивает доход и расход семьи; ошибка любой части не оставляет
частично проведённую операцию. Межбюджетные переводы проверяются отдельно, если включены в объём.

## 6. Общие планы

**Подтверждено:** существующие планы создаются и читаются по `userId`, используют личные категории
и личный сервис расходов. Групповых маршрутов планов нет.

**Предлагаемая доработка:**

- Добавить планы с владельцем-бюджетом `group`, автором, суммой, валютой, сроком и категорией группы.
- Описать список, детали, создание, изменение, архивирование/удаление и исполнение.
- Исполнение должно создавать или связывать расход того же группового бюджета с совместимым счётом.
- Уточнить возможность частичного исполнения, отличие запланированной суммы от фактической,
  отмену исполнения и судьбу связи при удалении/изменении расхода.
- Определить права управления планами других участников и отражение в отчётности: сам план
  не должен становиться фактическим расходом до исполнения.

**Приёмка:** план, созданный супругом, доступен супруге; уполномоченная супруга исполняет его из
семейного кошелька, расход учитывается один раз и не появляется в личном бюджете автора.

## 7. Общие долги

**Подтверждено:** существующие долги принадлежат `userId`; погашение связано с личным финансовым
сервисом. Групповых маршрутов долгов нет.

**Предлагаемая доработка:**

- Добавить долги с владельцем-бюджетом `group`, валютой, контрагентом, исходной и оставшейся суммой.
- Описать список, детали, изменение, закрытие/архивирование, историю и частичные погашения.
- Определить поддерживаемые направления: «нам должны», «мы должны» или оба. Не менять смысл
  существующего личного долга без отдельного решения.
- Связывать финансовое погашение со счётом и операцией соответствующего группового бюджета;
  явно описать, когда возникает доход, расход или иное движение.
- Изменение остатка долга и финансовая операция должны быть атомарными; определить отмену погашения
  и правила изменения/удаления связанной операции.
- Применить права совместного управления и сохранить историю после выхода автора из группы.

**Приёмка:** оба супруга видят один долг и его историю; погашение меняет семейный остаток и долг
согласованно, не затрагивая личные финансы участников.

## 8. Предпросмотр приглашения

**Подтверждено:** `GroupInvitationsController` предоставляет только `POST /group-invitations/accept`.
Название группы до вступления получить по токену нельзя. Токен возвращается только при создании,
ссылка одноразовая, срок — семь дней; открытие ссылки не означает принятие.

**Предлагаемая доработка:** отдельный безопасный запрос предпросмотра по токену в теле запроса,
например `POST /group-invitations/preview`. Вернуть минимальные сведения для осознанного согласия:
название, тип группы, срок действия; имя приглашающего — только после решения о приватности.

- Предпросмотр не создаёт членство и не потребляет приглашение.
- Решить, доступен ли он до авторизации; ограничить частоту и объём раскрываемых данных.
- Не раскрывать участников, суммы и другую финансовую информацию.
- Сохранить общий ответ для невалидных, истёкших, использованных, отозванных ссылок и удалённых групп.
- Успешный предпросмотр не гарантирует последующее принятие: ссылку могут отозвать или использовать.

**Приёмка:** получатель видит подтверждённое бэком название группы до нажатия «Вступить»;
просмотр не мешает последующему принятию действительного приглашения.

## 9. Контекст текущего участника и исторические имена

### 9.1. Эффективные права текущего пользователя

**Подтверждено:** ответ группы содержит `role`, но финансовые `permissions` находятся в пагинированном
списке участников. Получить их возможно, однако собственной записи может не быть на первой странице.

**Рекомендация:** включить текущие эффективные права в ответ группы либо добавить endpoint
текущего членства. При расширении модели прав вернуть также поддерживаемые возможности бюджета,
если фронту понадобится различать версии API. Сервер остаётся источником проверки доступа.

### 9.2. Имена бывших участников

**Подтверждено:** каталог участников содержит только действующих участников. Операции сохраняют
`createdBy` и `participantId`, включая исторические связи, но групповой сервис возвращает записи
без разрешения этих идентификаторов в имена. После выхода человека фронту может быть недоступно его имя.

**Рекомендация:** безопасные краткие сведения об исторических авторах/участниках в ответах операций
либо отдельное разрешение идентификаторов в пределах доступной финансовой истории. Определить
отображение удалённого пользователя и политику обновления/сохранения имени без раскрытия email.

## 10. Документация и проверка контракта

**Подтверждено:** начало `docs/groups-api.md` всё ещё говорит, что групповые счета и операции будут
добавлены отдельно, хотя `group-finances` уже реализован. Таблица групп не перечисляет маршрут
изменения финансовых прав, описанный в `docs/group-finances-api.md`.

После доработок необходимо:

- Обновить документы и действующие OpenSpec-спецификации бэка, не переписывая архивные изменения.
- Опубликовать точные запросы и ответы групповых API, включая пагинацию и ошибки.
- Проверить изоляцию личного бюджета и разных групп, права с прежним JWT, исторические записи,
  точность валют, атомарность и конкурентное исполнение финансовых действий.
- Проверить семейный сценарий двумя пользователями с разными личными настройками валюты.
- Определить совместимость и миграцию уже существующих групповых данных.

## Что уже поддержано и не требует нового API само по себе

- Создание, чтение, изменение и удаление групп; членство в нескольких группах.
- Создание, список состояний, отзыв и явное принятие одноразовых приглашений.
- Каталог действующих участников, выход, исключение, передача владения и три права финансовых настроек.
- Основной кошелёк, доходы, расходы, категории, лимиты, месячные и годовые групповые отчёты.
- Разделение личных и групповых финансов; сохранение истории при выходе/исключении.

Переключатель бюджета, отдельные ключи кэша, сохранение приглашения на время входа/регистрации,
возврат после регистрации и закрытие форм при смене бюджета — задачи фронта. Они не являются
недостатками API. Отсутствие кошелька после создания группы можно обработать первоначальной настройкой
на фронте, поэтому атомарное создание «группа + кошелёк» не является обязательной доработкой бэка.
